# [[沉浸式叙事体验]]

## 🎯 目标

> 在 XR 中构建叙事与空间融合的沉浸式体验，让观众成为故事的参与者而非旁观者。

**核心价值**：XR 叙事不是「把电影放进 VR 头盔」。空间、声音、运动都是叙事工具。本 Skill 将每个感官维度纳入叙事设计。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `narrative_type` | enum | ✅ | — | 类型：`linear`（线性）/ `branching`（分支）/ `exploratory`（探索式）/ `ambient`（环境叙事） |
| `xr_type` | enum | ❌ | `"vr"` | XR 类型：`vr` / `ar` / `mr` |
| `duration` | enum | ❌ | `"15min"` | 体验时长 |
| `emotion_target` | enum | ❌ | `"immersive"` | 情绪目标：`immersive`（沉浸）/ `emotional`（感动）/ `educational`（教育）/ `thrilling`（刺激） |
| `spatial_audio` | boolean | ❌ | `true` | 是否使用空间音频 |

## 📤 输出

```json
{
  "experience_design": {
    "narrative_arc": "string — 叙事弧线（起承转合）",
    "spatial_story_beats": [{"location": "string", "event": "string", "sensory": "string"}],
    "user_agency": "string — 用户参与度设计"
  },
  "spatial_audio_plan": {
    "ambient": "string — 环境音设计",
    "diegetic": ["string — 空间内音源"],
    "score": "string — 配乐设计"
  },

  }

```

## 📋 执行步骤

### Step 1: 空间叙事设计
1. **空间即剧本** — 每个房间/区域讲述故事的一部分
2. **用户路径** — 设计叙事引导，但允许自由探索
3. **时间控制** — 用空间移动而非计时器推进叙事
4. **检查点**：✅ 空间是否承载了叙事？用户是否有探索自由？

### Step 2: 多感官叙事
1. **空间音频** — 声音从空间中的具体位置传来
2. **视觉引导** — 光线/颜色/运动引导注意力
3. **触觉反馈** — 关键时刻的触觉增强
4. **环境效果** — 温度/风/气味（如有硬件支持）
5. **检查点**：✅ 是否利用了多种感官？音频是否空间化？

### Step 3: 舒适度与节奏
1. **叙事节奏** — 张弛有度，高强度段后有休息段
2. **移动控制** — 用户不主动移动时由叙事引导
3. **休息点** — 每 5-7 分钟设计一个自然的休息间隔
4. **检查点**：✅ 节奏是否有张弛？是否有休息点？

### Step 4: 用户参与
1. **互动节点** — 关键决策点让用户影响叙事
2. **发现奖励** — 探索发现额外的叙事内容
3. **情感高潮** — 设计一个记忆点（peak-end rule）
4. **检查点**：✅ 用户是否影响了叙事？是否有情感高潮？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 用户晕动 | 叙事引导移动导致 | 改为传送式移动或减少引导移动 |
| 叙事迷失 | 用户不知道该去哪 | 增加视觉/音频引导线索 |
| 情绪过载 | 高强度段过长 | 插入休息段，降低刺激强度 |

## 💬 沟通风格

- **空间思维**：用「房间/走廊/窗户/天花板」描述叙事
- **感官优先**：先设计用户看到/听到/感受到什么，再说技术实现
- **节奏为王**：叙事节奏匹配身体节奏，而非屏幕节奏

## 📝 自检清单

- [ ] 空间是否承载了叙事？
- [ ] 音频是否空间化？
- [ ] 叙事节奏是否有张弛？
- [ ] 是否有自然的休息点？
- [ ] 用户是否能影响叙事？
- [ ] 是否有记忆点（情感高潮）？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

**格式校验**：

**内容校验**：

**合规校验**：
- [ ] 未违反硬性约束

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
