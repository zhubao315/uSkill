# Select Thinking Methodology（思维方法论路由选择器）

## 🎯 目标
> 面对任意思维任务（表达、推理、学习、评估、写作），快速识别最适配的方法论框架，并提供结构化的执行指引。解决"知道很多方法论但临场不知道用哪个"的选择困难症，让14个思维框架成为随时可调用的"思维武器库"。

## 📥 输入

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task` | string | ✅ | 需要完成的思维任务描述（如"向领导汇报项目延期原因"、"分析这个投资决策"） |
| `context` | string | ❌ | 任务发生的背景信息（如受众、场合、时间压力） |
| `available_info` | array | ❌ | 已有的信息/素材列表，影响方法论选择 |
| `preferred_complexity` | enum | ❌ | `quick`（5分钟速查）/ `standard`（标准流程）/ `deep`（深度分析），默认 `standard` |
| `exclude_methods` | array | ❌ | 希望排除的方法论ID列表 |

## 🔢 执行步骤

1. **任务诊断** — 分析用户的 `task` 描述，识别任务类型（表达/推理/学习/评估/写作/规划）和核心挑战
2. **方法论匹配** — 基于任务类型从方法论索引表中筛选最佳匹配：
   - **需要说服/表达** → SCQA（先制造共鸣）或 STAR（用故事证明）
   - **需要逻辑推理** → 三段式推理（演绎，确保正确性）或 归纳法（发现新规律）
   - **需要学习/理解** → 费曼技巧（以教促学）或 强力研读法（深度阅读）
   - **需要写作/文档** → 写好文档的checklist（质量保障）或 SCQA（结构化表达）
   - **需要了解人** → MBTI（性格评估）或 STAR（行为分析）
   - **需要评估质量** → 金线（标准化评估）
   - **需要流程优化** → 接客流程优化 或 模板与套路
   - **需要知识管理** → DIKW（知识层次）或 飞阅会（高效会议）
   - **需要自我介绍/协作** → 个人说明书
3. **上下文校准** — 根据 `context` 和 `available_info` 调整推荐（如时间紧急偏向简单框架，受众非专业则避免复杂推理）
4. **生成执行指南** — 基于推荐方法论，输出具体执行步骤和关键提示词
5. **提供备选方案** — 列出 1-2 个备选方法论及切换条件，确保灵活性
6. **输出方法论简报** — 提供推荐方法论的核心框架、一句话概括和适用/不适用场景，帮助用户快速理解

## ⚠️ 异常处理

| 异常场景 | 处理方式 |
|----------|----------|
| 任务描述模糊，无法判断类型 | 追问 2-3 个澄清问题：目标是什么？受众是谁？时间限制？ |
| 任务需要多个方法论组合 | 推荐主方法论 + 协作方法论，说明组合顺序和衔接点 |
| 用户要求的方法论不适合当前任务 | 明确说明不匹配原因，推荐更适合的方法论 |
| `exclude_methods` 排除了所有匹配项 | 返回最接近的剩余选项并说明推荐度降低的原因 |
| 任务超出14个方法论覆盖范围 | 推荐最接近的方法论，建议用户参考「模板与套路」自建新框架 |
| 用户对推荐结果不满意 | 提供方法论对比表，让用户自行选择 |

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：

**内容校验**：

**合规校验**：
- [ ] 未违反硬性约束

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
