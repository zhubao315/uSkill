# 地理空间数据工程

## 🎯 目标

> 构建可靠的地理空间数据基础设施，从采集、清洗、存储到服务的全链路管道化。

**核心价值**：GIS 应用的数据 80% 时间在管道里，20% 时间在地图上。本 Skill 将数据管道标准化，确保数据始终新鲜、一致、可用。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `source_type` | enum | ✅ | — | 数据源：`file`（文件）/ `api`（API）/ `database`（数据库）/ `stream`（实时流） |
| `source_config` | object | ✅ | — | 数据源连接配置 |
| `target_store` | enum | ❌ | `"postgis"` | 目标存储：`postgis` / `geopackage` / `parquet` / `s3` |
| `transform_rules` | array | ❌ | — | 转换规则列表（CRS 转换/字段映射/过滤条件） |
| `schedule` | string | ❌ | `"on_demand"` | 调度频率：`on_demand` / `daily` / `hourly` / `realtime` |

## 📤 输出

```json
{
  "pipeline_config": {
    "source": "string — 数据源配置摘要",
    "transforms": ["string — 已应用的转换步骤"],
    "target": "string — 目标存储配置摘要"
  },
  "data_profile": {
    "feature_count": "int — 要素数",
    "crs": "string — 坐标系",
    "bbox": "string — 空间范围",
    "attribute_completeness": "float — 属性完整率",
    "freshness": "string — 数据新鲜度"
  },
  "pipeline_id": "string — 管道唯一标识",
  "schedule_next": "string — 下次执行时间"
}
```

## 📋 执行步骤

### Step 1: 数据源评估
1. **连接测试** — 验证数据源可达性和格式兼容性
2. **数据探查** — 读取样本数据，了解结构、字段、数据类型
3. **质量基线** — 记录当前数据质量指标（完整性/一致性/时效性）
4. **检查点**：✅ 数据源是否可达？数据结构是否已了解？

### Step 2: 管道设计
1. **CRS 策略** — 统一到目标 CRS，记录转换参数
2. **字段映射** — 源字段 → 目标字段，含类型转换和默认值
3. **过滤规则** — 无效几何跳过、空属性处理策略
4. **容错机制** — 单条失败不中断整个管道，记录错误日志
5. **检查点**：✅ 管道是否有容错？CRS 转换参数是否记录？

### Step 3: 存储与索引
1. **PostGIS 建表** — 空间字段类型（geometry/ geography）、CRS 元数据
2. **空间索引** — 创建 GIST 索引，加速空间查询
3. **属性索引** — 对常用查询字段创建 B-Tree 索引
4. **数据分区** — 大表按时间/区域分区
5. **检查点**：✅ 空间索引是否创建？查询性能是否达标？

### Step 4: 监控与维护
1. **管道监控** — 记录每次执行的状态、耗时、处理条数
2. **数据新鲜度** — 监控数据更新时间，超期报警
3. **血缘追踪** — 记录每个数据集的来源、转换历史
4. **定期清理** — 归档过期数据，清理临时文件
5. **检查点**：✅ 监控是否到位？血缘是否可追溯？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 数据源不可达 | 连接超时/认证失败 | 重试 3 次后报警，记录错误日志 |
| CRS 转换失败 | 坐标系不识别 | 回退到源 CRS，标记需要人工处理 |
| 数据量暴增 | 超过预期 2 倍 | 启动限流处理，防止内存溢出 |
| 存储空间不足 | PostGIS 磁盘 >80% | 归档历史数据，通知管理员 |

## 💬 沟通风格

- **工程思维**：每个环节都要有监控和告警
- **数据血缘**：任何数据变更都能追溯到源头
- **务实主义**：先保证管道跑通，再优化性能

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据
