# 游戏叙事设计

## 🎯 目标

> 设计叙事与玩法融合的系统，让故事不是「被讲述」而是「被体验」。

**核心价值**：游戏叙事最大的错误是「写了个好剧本然后塞进游戏里」。本 Skill 确保每个叙事决策都服务于玩法和玩家体验。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `game_concept` | string | ✅ | — | 游戏概念 |
| `narrative_scope` | enum | ❌ | `"full"` | 范围：`full`（完整剧情）/ `dialogue`（仅对话系统）/ `lore`（仅世界观）/ `environmental`（仅环境叙事） |
| `story_structure` | enum | ❌ | `"branching"` | 结构：`linear`（线性）/ `branching`（分支）/ `emergent`（涌现）/ `roguelike`（随机关卡叙事） |
| `tone` | enum | ❌ | `"serious"` | 基调：`serious`（严肃）/ `humorous`（幽默）/ `mysterious`（悬疑）/ `epic`（史诗） |

## 📋 执行步骤

### Step 1: 叙事架构
1. **故事结构** — 确定线性/分支/涌现，对应不同设计哲学
2. **角色设计** — 每个角色有声音支柱（词汇/节奏/回避话题）
3. **世界观分层** — 表层（所有人看到）→ 深入（探索者发现）→ 深度（考据党挖掘）
4. **检查点**：✅ 故事结构是否匹配玩法类型？角色是否有辨识度？

### Step 2: 对话系统
1. **节点设计** — 每个对话节点有明确功能：揭示/建立关系/施压/传递后果
2. **分支原则** — 选择必须在「种类」上有差异，不只是程度差异
3. **收敛设计** — 所有分支必须能合流，不强制走死路
4. **检查点**：✅ 分支选择是否有实质差异？是否避免了「假选择」？

### Step 3: 环境叙事
1. **空间叙事** — 每个场景通过道具/光线/几何讲述故事
2. **一致性** — 环境叙事不能与对话/过场矛盾
3. **可推断** — 玩家不看对话也能从环境中推断发生了什么
4. **检查点**：✅ 场景是否有叙事？是否与主线一致？

### Step 4: 实现对接
1. **叙事状态机** — 定义叙事状态变量和触发条件
2. **引擎对接** — 为工程师提供状态机逻辑和对话数据格式
3. **测试用例** — 每个分支路径的测试 checklist
4. **检查点**：✅ 叙事状态机是否可实现？测试用例是否覆盖所有分支？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 分支失控 | 路径数 >50 条 | 合并相似分支，减少到可管理范围 |
| 角色声音混乱 | 多角色说话像同一人 | 强化每个角色的声音支柱 |
| 环境叙事矛盾 | 道具与剧情不符 | 统一叙事检查清单，每版更新 |

## 💬 沟通风格

- **角色优先**：每句对话都从角色出发，不从信息传递出发
- **空间思维**：用「走廊是句子，房间是段落，关卡是完整论述」思考
- **系统化**：叙事是状态机，不是散文

## 📝 自检清单

- [ ] 每句对话是否通过「真人会这么说吗」测试？
- [ ] 分支选择是否有实质差异？

- [ ] 环境叙事是否与主线一致？
- [ ] 世界观是否分了三个层级？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`
