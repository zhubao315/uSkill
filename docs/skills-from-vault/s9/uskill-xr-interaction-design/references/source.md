# XR 交互设计

## 🎯 目标

> 设计符合人体工学和认知习惯的沉浸式交互系统，让技术退到背景，体验走到前台。

**核心价值**：XR 交互最大的敌人是「晕」和「困惑」。本 Skill 将交互设计约束在人体可承受范围内。

**适用场景**：
- VR 培训/教育应用
- AR 工业巡检/远程协作
- 空间计算应用（visionOS）
- 城市规划/建筑的 XR 可视化

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `xr_type` | enum | ✅ | — | 类型：`vr`（完全沉浸）/ `ar`（增强现实）/ `mr`（混合现实）/ `spatial`（空间计算） |
| `interaction_mode` | enum | ❌ | `"hand_tracking"` | 交互：`hand_tracking` / `controller` / `eye_tracking` / `voice` / `hybrid` |
| `target_device` | enum | ❌ | `"quest3"` | 设备：`quest3` / `visionpro` / `hololens` / `generic` |
| `session_duration` | enum | ❌ | `"30min"` | 单次使用时长 |
| `comfort_level` | enum | ❌ | `"medium"` | 舒适度要求 |

## 📋 执行步骤

### Step 1: 交互范式选择
1. **输入方式** — 手势追踪/控制器/眼动/语音，根据场景组合
2. **交互距离** — 近距离（臂展内）/ 中距离 / 远距离
3. **反馈设计** — 触觉反馈 + 视觉反馈 + 空间音频反馈
4. **检查点**：✅ 输入方式是否自然？反馈是否多模态？

### Step 2: 空间界面设计
1. **信息层级** — 主界面/工具面板/信息卡片的空间位置
2. **手势可达** — 常用操作在舒适区（腹部到肩部高度）
3. **空间锚定** — 信息固定在空间中还是跟随用户
4. **检查点**：✅ 界面是否在舒适区内？是否考虑了不同身高？

### Step 3: 舒适度保障
1. **移动方式** — 优先传送/瞬移，减少晕动
2. **帧率保障** — VR ≥72fps，AR/MR ≥60fps
3. **视觉稳定** — HUD 元素固定在头部而非世界，减少晕动
4. **休息点** — 长时间使用设计自然的休息间隔
5. **检查点**：✅ 移动方式是否防晕？帧率是否达标？

### Step 4: 无障碍与测试
1. **单手模式** — 支持单手操作
2. **语音备选** — 所有操作有语音替代方案
3. **舒适度测试** — 邀请 5+ 用户测试，收集舒适度反馈
4. **检查点**：✅ 是否有无障碍方案？舒适度测试是否通过？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 用户晕动 | 晕动症报告 | 立即暂停，降低移动速度，切换到传送模式 |
| 手势识别差 | 识别率 <80% | 增大按钮尺寸，增加容错范围 |
| 帧率不稳 | <目标帧率 | 降低渲染质量，减少同屏物体数 |

## 💬 沟通风格

- **身体优先**：先考虑人体工学，再考虑技术实现
- **防晕为王**：任何可能导致晕动的设计都要重新评估
- **自然交互**：让用户做他在现实中会做的事

## 📝 自检清单

- [ ] 交互是否符合人体自然运动模式？
- [ ] 帧率是否达标（VR ≥72fps）？
- [ ] 移动方式是否防晕动？
- [ ] 是否有无障碍方案？
- [ ] 舒适度测试是否通过？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
