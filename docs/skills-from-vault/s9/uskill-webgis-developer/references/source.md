# WebGIS 开发

## 🎯 目标

> 构建高性能、跨平台、交互流畅的 Web 地图应用，从数据服务到前端渲染全链路标准化。

**核心价值**：WebGIS 最常见的失败是「数据加载慢、交互卡顿、移动端崩溃」。本 Skill 将性能优化前置，确保应用在真实网络和设备上可用。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `app_type` | enum | ✅ | — | 应用类型：`dashboard`（仪表盘）/ `explorer`（数据浏览）/ `editor`（数据编辑）/ `tracker`（实时追踪） |
| `data_source` | string | ✅ | — | 数据源（GeoJSON URL / WMS / 矢量瓦片 / PostGIS） |
| `map_library` | enum | ❌ | `"maplibre"` | 地图库：`maplibre`（推荐）/ `leaflet` / `arcgis-js` / `deck.gl` |
| `features` | array | ❌ | `["zoom","pan","identify","search"]` | 功能列表 |
| `target_devices` | array | ❌ | `["desktop","mobile"]` | 目标设备 |
| `realtime` | boolean | ❌ | `false` | 是否需要实时数据更新 |

## 📋 执行步骤

### Step 1: 技术选型
1. **地图库选择** — MapLibre GL JS（开源、矢量瓦片、3D 支持）首选
2. **数据服务** — 小数据 GeoJSON 直接加载；大数据矢量瓦片 + Martin/Tippecanoe
3. **框架搭配** — React/Next.js + MapLibre GL JS，状态管理用 Zustand
4. **检查点**：✅ 技术栈是否匹配数据量和性能需求？

### Step 2: 数据层设计
1. **瓦片策略** — <1万要素直接 GeoJSON；>1万用矢量瓦片
2. **聚合方案** — 缩放层级高时聚合点要素，降低渲染压力
3. **视口过滤** — 只加载当前视口范围内的要素
4. **缓存策略** — 瓦片缓存 + Service Worker 离线支持
5. **检查点**：✅ 大数据量下是否仍有流畅交互？

### Step 3: 交互开发
1. **基础交互** — 平移、缩放、点击识别、搜索
2. **高级交互** — 测量、框选、图层切换、时间滑块
3. **响应式** — 桌面/平板/手机三端适配，触摸手势支持
4. **加载状态** — 骨架屏或进度条，不让用户面对空白地图
5. **检查点**：✅ 移动端触摸操作是否完整？加载状态是否可见？

### Step 4: 性能优化与部署
1. **渲染优化** — 限制同时渲染的要素数，使用数据驱动样式
2. **懒加载** — 非首屏图层延迟加载
3. **性能监控** — 记录首屏时间、帧率、内存占用
4. **部署** — Vercel/Cloudflare Pages + CDN 加速瓦片
5. **检查点**：✅ 首屏加载是否 <3s？移动端是否不崩溃？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 渲染卡顿 | >5万要素直接加载 | 切换矢量瓦片 + 聚合方案 |
| 移动端崩溃 | 内存溢出 | 限制图层数量、降低瓦片分辨率 |
| 瓦片加载慢 | CDN 未配置 | 配置瓦片缓存和 CDN 加速 |
| 数据更新延迟 | 实时数据不刷新 | 实现 WebSocket 推送或缩短轮询间隔 |

## 💬 沟通风格

- **性能优先**：每个方案都先评估性能影响
- **用户视角**：从用户操作路径出发设计交互，不从技术架构出发
- **渐进增强**：先保证基础功能可用，再叠加高级特性

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据
