# ☠️ uSkill-7104: 存在性风险扫描（Gen3）

## 🎯 目标

> 识别低概率高影响事件，评估最坏情景，生成"预防—检测—响应—恢复"四步应急预案，
> 让系统在真正的尾部冲击到来前具备韧性。

**适用场景**：[[uLife OS]] 知识库（Obsidian + Syncthing）数据资产保全、个人投资系统
（见 [[我的交易系统]]、[[对冲信号监测器]]）回撤与集中度风险、线上服务可用性。

---

## 📥 输入

| 参数 | 类型 | 必填 | 说明 |
|------|------|:----:|------|
| `system` | `string` | ✅ | 系统描述（含关键依赖） |
| `status` | `object` | ✅ | 当前状态数据（资产/备份/集中度/依赖） |
| `horizon` | `string` | ❌ | 评估时间窗，默认 `12m` |

---

## 📤 输出

```json
{
  "risks": [
    {"risk": "string", "layer": "技术|运营|市场|外部", "probability": "极低|低|中|高", "impact": "可忽略|中等|严重|致命", "mitigation": "string"}
  ],
  "worst_case": "string",
  "defense_measures": [{"phase": "预防|检测|响应|恢复", "action": "string"}],
  "early_warning_signals": ["string"]
}
```

## 🔄 执行流程

```
1. [风险扫描] → 四层扫描系统脆弱点
    → 技术层：数据丢失、系统崩溃、安全漏洞、单点依赖
    → 运营层：关键人离开、资金链断裂、流程失效
    → 市场层：竞品颠覆、政策变化、系统性回调
    → 外部层：自然灾害、法律诉讼、供应链中断
    → IF 系统依赖外部 API：必查 API 停服/限流/涨价风险
    → IF 系统存储用户/个人数据：必查隐私合规与勒索风险

2. [概率评估] → 量化每个风险发生概率
    → 极低：<1%/年 | 低：1-5% | 中：5-20% | 高：>20%
    → IF 历史曾发生同类事件：概率上调一档

3. [影响评估] → 量化最坏影响
    → 可忽略：轻微不便 | 中等：需额外资源 | 严重：核心功能受损 | 致命：系统无法运行
    → IF impact=致命：强制进入应急预案分支（不可跳过）

4. [应急预案] → 四步法生成
    → 预防：降低发生概率的具体动作
    → 检测：可观测的早期预警信号
    → 响应：发生后的前 30 分钟处置步骤
    → 恢复：回到正常运营的回滚/重建步骤
    → THEN 输出 预防+检测+响应+恢复 四段方案

5. [输出报告] → 风险清单 + 最坏情景 + 防御措施 + 预警信号
    → IF 任一风险 impact=致命：报告顶部用 ☠️ 高亮
```

## 📝 Prompt 模板

### 标准扫描 Prompt

```
你是存在性风险扫描 Agent。请扫描以下系统的存在性风险。

【系统描述】{system}
【当前状态】{status}
【评估窗口】{horizon}

【扫描维度】
1. 技术风险：数据、安全、可用性、外部依赖
2. 运营风险：人员、资金、流程
3. 市场风险：竞争、政策、趋势
4. 外部风险：自然、法律、供应链

【风险分级】
- 致命：系统无法运行 | 严重：核心功能受损
- 中等：需额外资源 | 可忽略：轻微不便

【硬性要求】
- 致命风险必须给出 预防/检测/响应/恢复 四步预案
- 每个风险须给出可观测的早期预警信号

【输出格式】
严格按标准 JSON 输出，包含 risks、worst_case、defense_measures、early_warning_signals。
```

## ⚠️ 异常处理

| 异常场景 | 处理方式 | 降级策略 |
|----------|----------|----------|
| 系统信息不完整 | 基于已有信息评估 | 标注"信息不完整"，缺口列明 |
| 无法评估概率 | 标为"待评估" | 用历史同类事件推断并标注置信度 |
| 多致命风险叠加 | 按影响×概率排序 | 输出优先级处置序列 |
| 涉及监管/法律 | 仅给框架不替决策 | 强制转人工合规审查 |

- [ ] 四层（技术/运营/市场/外部）均已覆盖，无遗漏

- [ ] 致命风险 100% 有四步预案

#### ⚠️ 边界约束

**硬性约束（必须遵守）**：
1. 不得代替用户做不可逆的金融/法律决策
2. 不得泄露个人资产、身份等隐私数据
3. 致命风险预案仅为建议，**必须**经用户确认后执行

**软性约束（建议遵守）**：
1. 优先用历史真实事件校准概率，避免拍脑袋
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认
- 当多个致命风险同时存在且资源冲突时，**必须**转人工定优先级

#### ✅ 校验验收规则

**格式校验**：
- [ ] 输出结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义 JSON 规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化（如监管、平台政策）

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

- [ ] 核心输出已生成
- [ ] 输出格式符合预期

### 失败处理
