# [[游戏系统设计]]

## 🎯 目标

> 将创意愿景转化为可执行的设计文档，让工程师和美术无需猜测即可实现。

**核心价值**：好游戏不是堆功能，是设计「让人想再玩一局」的循环。本 Skill 将每个设计决策文档化、可测试、可平衡。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `game_concept` | string | ✅ | — | 游戏概念（一句话说清是什么游戏） |
| `genre` | enum | ✅ | — | 类型：`rpg` / `action` / `puzzle` / `strategy` / `roguelike` / `platformer` / `simulation` |
| `target_platform` | enum | ❌ | `"pc"` | 平台：`pc` / `mobile` / `console` / `web` |
| `design_scope` | enum | ❌ | `"full"` | 范围：`full`（完整 GDD）/ `core_loop`（仅核心循环）/ `economy`（仅经济系统）/ `progression`（仅成长系统） |
| `team_size` | int | ❌ | `1` | 团队规模 |

## 📤 输出

```json
{
  "gdd": {
    "concept": "string — 游戏概念",
    "core_loop": {
      "moment_to_moment": "string — 即时操作循环",
      "session": "string — 单局循环",
      "long_term": "string — 长期目标循环"
    },
    "mechanics": [{"name": "string", "purpose": "string", "inputs": "string", "outputs": "string", "edge_cases": ["string"]}],
    "economy": {"currencies": ["string"], "sinks": ["string"], "faucets": ["string"], "balance_notes": "string"},
    "progression": {"curve": "string", "milestones": ["string"], "monetization": "string"}
  },
  "balance_spreadsheet": "string — 数值平衡表路径",
  "prototype_plan": "string — 纸面/数字原型方案"
}
```

## 📋 执行步骤

### Step 1: 概念与核心循环
1. **一句话定义** — 用「玩家扮演 X，在 Y 中做 Z，因为 W 很有趣」格式
2. **核心循环拆解** — 即时（秒级操作）→ 单局（分钟级目标）→ 长期（小时级追求）
3. **动机映射 — **每个循环层级对应哪种玩家动机（成就/探索/社交/竞争）
4. **检查点**：✅ 核心循环是否在 30 秒内可理解？动机是否清晰？

### Step 2: 机制设计
1. **机制清单** — 列出所有核心机制（移动/战斗/建造/交易等）
2. **交互矩阵** — 机制之间如何互相影响
3. **边缘情况** — 每个机制的极端情况和失败状态
4. **检查点**：✅ 每个机制是否有明确的输入/输出？是否有边缘情况文档？

### Step 3: 经济与平衡
1. **货币体系** — 货币类型、获取途径（水龙头）、消耗途径（水池）
2. **数值假设** — 所有数值标记为 `[PLACEHOLDER]`，直到测试验证
3. **平衡表** — 建立数值平衡电子表格，监控通胀/通缩
4. **检查点**：✅ 经济是否有水龙头/水池模型？数值是否有假设依据？

### Step 4: 文档化与原型
1. **GDD 撰写** — 按标准模板撰写游戏设计文档
2. **纸面原型** — 在实现前先用纸面/表格验证核心循环
3. **版本管理** — GDD 是活文档，每次重大修改记录 changelog
4. **检查点**：✅ GDD 是否无实现歧义？纸面原型是否验证过？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 经济崩溃 | 通胀率 >50%/小时 | 增加消耗途径或减少产出 |
| 玩家流失 | 单局留存 <30% | 强化核心循环的即时反馈 |
| 机制冲突 | 两个机制互相矛盾 | 重新评估机制优先级，合并或删除 |

## 💬 沟通风格

- **从玩家出发**：先说「玩家感受到什么」，再说「系统怎么实现」
- **数值有据**：每个数字都有设计依据，不用「感觉差不多」
- **文档化一切**：设计决策不留在脑子里，写下来供团队执行

## 📝 自检清单

- [ ] 核心循环是否在 30 秒内可理解？
- [ ] 每个机制是否有输入/输出/边缘情况文档？
- [ ] 所有数值是否标记为 PLACEHOLDER 直到测试？
- [ ] 经济系统是否有水龙头/水池模型？
- [ ] GDD 是否无实现歧义？
- [ ] 纸面原型是否验证过核心循环？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
