# 多人联网系统设计

## 🎯 目标

> 构建安全、低延迟、防作弊的多人游戏联网系统，让玩家感受不到网络的存在。

**核心价值**：多人游戏最致命的问题不是延迟本身，而是延迟导致的状态不一致和作弊漏洞。本 Skill 将服务器权威架构标准化，确保「服务器拥有真相」。

## 📋 执行步骤

### Step 1: 权威模型设计
1. **服务器权威** — 服务器拥有所有游戏状态的绝对权威
2. **客户端职责** — 客户端只发送输入（按键/方向），不发送位置
3. **状态复制** — 服务器将权威状态广播给所有客户端
4. **检查点**：✅ 服务器是否拥有所有状态的权威？客户端是否只发输入？

### Step 2: 客户端预测与调和
1. **本地预测** — 客户端根据本地输入立即执行，不等服务器确认
2. **服务器确认** — 服务器返回权威状态，客户端对比本地预测
3. **不一致处理** — 如果预测错误，回滚到服务器状态重新模拟
4. **插值平滑** — 对其他玩家使用插值，减少视觉抖动
5. **检查点**：✅ 预测是否在 150ms 延迟下测试？调和是否平滑？

### Step 3: 反作弊架构
1. **服务器验证** — 所有客户端发来的数据都必须在服务器端验证
2. **输入验证** — 检查输入是否在合法范围内（移动速度/攻击频率）
3. **状态校验** — 定期校验客户端状态与服务器状态是否一致
4. **检测机制** — 统计异常行为（命中率异常/移动速度异常）
5. **检查点**：✅ 是否有服务器验证？是否有统计检测？

### Step 4: 匹配与重连
1. **匹配系统** — 基于 ELO/段位/延迟的匹配算法
2. **房间管理** — 房间创建/加入/离开/销毁的生命周期
3. **断线重连** — 保存游戏状态快照，允许断线后恢复
4. **检查点**：✅ 匹配是否考虑延迟？断线是否可重连？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 状态不同步 | 客户端状态与服务器不一致 | 强制客户端同步到服务器状态 |
| 延迟飙升 | >200ms | 启用延迟补偿、调整插值缓冲 |
| 作弊检测 | 统计异常 | 警告/踢出/封禁分级处理 |

## 💬 沟通风格

- **延迟思维**：每个设计决策都考虑 100-200ms 延迟下的表现
- **安全第一**：不信任任何来自客户端的数据
- **量化指标**：不说「感觉同步了」，说「状态差异 <3 个帧」

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |
