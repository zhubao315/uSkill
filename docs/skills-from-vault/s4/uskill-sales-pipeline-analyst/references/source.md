# [[销售漏斗管理]]

## 🎯 目标

> 将销售过程从「感觉」转化为「数据」，精准定位瓶颈并持续优化。

**核心价值**：大多数销售团队不知道自己的漏斗哪里漏水。本 Skill 将漏斗量化为可诊断、可预测的系统。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `pipeline_data` | string | ✅ | — | 漏斗数据（CRM 导出/手动输入） |
| `stage_definition` | array | ❌ | `["lead","qualified","proposal","negotiation","closed"]` | 销售阶段定义 |
| `forecast_period` | enum | ❌ | `"monthly"` | 预测周期：`weekly` / `monthly` / `quarterly` |
| `revenue_target` | int | ❌ | — | 目标收入 |

## 📤 输出

```json
{
  "funnel_analysis": {
    "stage_conversion": [{"from": "string", "to": "string", "rate": "float", "avg_days": "int"}],
    "bottleneck": "string — 最大卡点环节",
    "drop_off_reasons": ["string — 客户流失原因"]
  },
  "forecast": {
    "weighted_pipeline": "int — 加权管线价值",
    "best_case": "int",
    "worst_case": "int",
    "confidence": "string"
  },
  "optimization_actions": [{"action": "string", "target_stage": "string", "expected_impact": "string"}]
}
```

## 📋 执行步骤

### Step 1: 漏斗健康诊断
1. **阶段转化率** — 计算每两个相邻阶段之间的转化率
2. **停留时长** — 每个阶段的平均停留天数
3. **流失分析** — 哪个阶段流失最多客户，流失原因是什么
4. **检查点**：✅ 最大卡点是否定位？流失原因是否明确？

### Step 2: 收入预测
1. **加权管线** — 每个阶段的商机 × 对应转化率 = 加权价值
2. **历史校准** — 用过去 3 个月的实际转化率校准预测
3. **情景分析** — 最佳/基准/最差三种情景
4. **检查点**：✅ 预测是否基于历史数据？是否有情景分析？

### Step 3: 瓶颈修复
1. **卡点针对** — 针对最大卡点制定具体改进动作
2. **流程优化** — 简化不必要的审批/等待环节
3. **赋能提升** — 为销售团队提供卡点环节的工具/话术/培训
4. **检查点**：✅ 改进动作是否具体可执行？是否有责任人？

### Step 4: 持续监控
1. **周度 review** — 每周更新漏斗数据，追踪变化
2. **异常报警** — 转化率异常下降时自动提醒
3. **季度复盘** — 每季度回顾预测准确度，校准模型
4. **检查点**：✅ 是否有固定的 review 节奏？异常是否及时发现？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 数据不完整 | 商机阶段信息缺失 | 标记数据缺口，基于已有数据估算 |
| 预测偏差大 | 偏差 >30% | 校准历史转化率，调整权重系数 |
| 集中度风险 | 单一客户 >30% | 分散风险，增加小客户管线 |

## 💬 沟通风格

- **数据驱动**：每个结论附带转化率和数字
- **可执行**：建议必须具体到「谁做什么」
- **前瞻预测**：不只看当前，还要预测未来

## 📝 自检清单

- [ ] 每个阶段的转化率是否已计算？
- [ ] 最大卡点是否已定位？

- [ ] 改进动作是否具体可执行？
- [ ] 是否有固定的周度 review 节奏？

- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理

- 绝不伪装成功
