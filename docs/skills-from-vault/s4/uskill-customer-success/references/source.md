# [[客户成功与扩展]]

## 🎯 目标

> 从「被动响应问题」转向「主动推动客户成功」，将客户成功转化为可预测的收入增长。

**核心价值**：获客成本是维护成本的 5-7 倍。本 Skill 将客户成功系统化，确保客户用得好、续得上、买得多。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `customer_data` | string | ✅ | — | 客户数据（使用量/合同/沟通记录） |
| `health_metric` | enum | ❌ | `"composite"` | 健康度：`composite`（综合评分）/ `usage`（使用量）/ `nps`（满意度） |
| `goal` | enum | ❌ | `"retention"` | 目标：`retention`（留存）/ `expansion`（扩展）/ `rescue`（挽回） |
| `contract_end` | string | ❌ | — | 合同到期日 |

## 📤 输出

```json
{
  "health_score": {
    "score": "int — 客户健康度 (0-100)",
    "factors": {"usage": "int", "engagement": "int", "support_tickets": "int", "payment": "int"},
    "risk_level": "string — 高/中/低"
  },
  "success_plan": {
    "onboarding": "string — 上线计划（新客户）",
    "adoption_milestones": ["string — 使用里程碑"],
    "qbr_agenda": "string — 季度业务回顾议程"],
    "expansion_opportunity": "string — 扩展机会分析"
  },
  "churn_prevention": {
    "warning_signs": ["string — 流失预警信号"],
    "intervention_plan": "string — 干预方案"
  }
}
```

## 📋 执行步骤

### Step 1: 客户健康度评估
1. **使用量** — 登录频率/功能使用深度/关键功能使用率
2. **参与度** — 邮件打开率/会议出席率/互动频率
3. **支持工单** — 工单数量/严重程度/解决满意度
4. **付款** — 付款是否及时/是否有争议
5. **检查点**：✅ 健康度评分是否有数据支撑？风险等级是否明确？

### Step 2: 成功计划
1. **新客户上线** — 30/60/90 天上线里程碑
2. **使用引导** — 确保客户用到核心功能
3. **季度回顾** — QBR 用数据展示价值，而非主观感受
4. **检查点**：✅ 上线里程碑是否明确？QBR 是否有数据支撑？

### Step 3: 扩展挖掘
1. **使用数据挖掘** — 哪些功能用量接近上限？
2. **痛点发现** — 客户的新需求是否可以通过扩展满足
3. **升级路径** — 设计自然的升级路径，而非硬推
4. **检查点**：✅ 扩展机会是否有数据支撑？升级路径是否自然？

### Step 4: 流失预防
1. **预警信号** — 使用量下降/会议不出席/工单增多
2. **干预时机** — 合同到期前 90 天启动挽回
3. **挽回方案** — 针对具体原因制定挽留方案
4. **检查点**：✅ 预警信号是否已定义？干预是否及时？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 健康度骤降 | 评分下降 >20 | 立即安排客户成功经理介入 |
| 流失高风险 | 健康度 <40 | 启动挽回流程，高层介入 |
| 扩展受阻 | 客户预算冻结 | 降低门槛，提供灵活方案 |

## 💬 沟通风格

- **价值导向**：每次沟通都展示客户获得了什么价值
- **数据说话**：用使用数据而非主观感受评估客户
- **预防优先**：在问题发生前解决，而非等客户投诉

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
