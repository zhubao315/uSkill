# 最小可行产品 MVP 定义

MVP 不是"功能少的产品"，而是"验证最关键假设所需的最小实验"。太多团队把 MVP 做成了"功能阉割版的产品"，丢失了验证目的本身。

## 核心方法

1. **假设排雷** — 列出产品的所有关键假设（价值假设：用户需要这个吗？增长假设：用户怎么找到我们？可行性假设：我们能做出来吗？），然后找出最不确定的那个——这就是 MVP 要验证的目标。

2. **痛点到功能映射** — 从用户痛点出发，逆向推导：为了验证"这个痛点真实且用户愿意解决"，最少需要做什么？每个功能必须对应一个待验证的假设，没有假设对应的功能就是浪费。

3. **MVP 类型选择** — 根据验证目标选择形态：
   - **落地页**：验证需求存在（先做宣传页面看转化率）
   - **Wizard of Oz**：人工在后台模拟产品功能，验证价值主张
   - **走廊测试**：手动服务少数用户，验证流程可行性
   - **原型**：可交互原型验证可用性和设计方向

4. **验证标准前置** — 在做 MVP 之前就定义"什么算验证通过"。例如："30% 的落地页访客点击注册按钮"或"5 个用户中至少 3 个愿意付费"。没有标准，验证就是自欺欺人。

5. **闭环时间 ≤ 2 周** — 从 MVP 上线到拿到可判断结果的时间不超过 2 周。超过 2 周说明 MVP 太大，需要进一步裁剪。速度比完美重要。

## 关键认知

MVP 的价值不在于它"做出来"的产品，而在于它"验证了/证伪了"的假设。**最成功的 MVP 是那些让你快速发现方向错了的 MVP**——因为它帮你节省了做完整产品的时间。

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🎯 技能概述

> 本技能提供 通用 领域的标准化操作流程，帮助用户高效完成相关任务。

**核心价值**：将复杂操作标准化为可重复执行的步骤，降低出错率，提升效率。

**适用场景**：
1. 日常操作执行
2. 新手快速上手
3. 质量一致性保证

## 🧪 Self-Play 测试用例

| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |
