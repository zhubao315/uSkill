
# OKR制定与执行

> 目标与关键结果管理法——将模糊愿景转化为可衡量、可追踪的季度执行体系。

## 核心公式

**O（目标）**：定性、鼓舞人心、有挑战性
**KR（关键结果）**：定量、可衡量、有截止时间

```
O: 成为团队中最可靠的交付者
  KR1: 连续 3 个季度按时交付率 ≥ 95%
  KR2: 代码 review 反馈问题数下降 40%
  KR3: 主导完成 1 个跨团队协作项目
```

## 制定原则

| 原则 | 说明 |
|------|------|
| 少即是多 | 每人每季 2-3 个 O，每个 O 2-4 个 KR |
| 挑战性 | 目标应让人感到 70% 把握（Google 标准） |
| 可衡量 | KR 必须有数字或明确的完成标志 |
| 自下而上 | 50% 目标由个人/团队自提，非上级指派 |

## 执行节奏

1. **季度初**：制定 OKR，全员可见
2. **每周**：进度更新（红/黄/绿状态）
3. **月中**：检查 KR 趋势，必要时调整策略
4. **季度末**：评分（0-1.0）+ 复盘

## 常见误区

- ❌ OKR = KPI（OKR 是目标管理，不是绩效考核）
- ❌ KR 写成任务（「完成 X」是任务，「X 指标提升 Y%」是 KR）
- ❌ 设定后不追踪（每周不 review 的 OKR 等于没有）

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📊 执行规范

**输入验证**：
- 必填参数检查：缺失时返回明确错误提示
- 类型校验：参数类型不匹配时返回类型错误
- 范围校验：数值超出合理范围时返回范围提示
- 格式校验：不符合预期格式时给出格式示例

**执行约束**：
- 单次执行超时：30 秒（可配置）
- 最大重试次数：3 次
- 并发限制：同一资源不并发写入
- 幂等性：相同输入产生相同输出

**输出规范**：
- 格式：JSON 结构化输出
- 必含字段：status/message/data/timestamp
- 错误输出：error_code/error_message/suggestion
- 日志：执行过程关键节点记录

## 📈 质量指标

| 指标 | 计算方式 | 目标 | 告警阈值 |
|------|---------|:----:|:--------:|
| 成功率 | 成功次数 / 总执行次数 | ≥ 95% | < 90% |
| 平均耗时 | 总耗时 / 执行次数 | < 10s | > 30s |
| 错误率 | 错误次数 / 总执行次数 | < 5% | > 10% |
| 重试率 | 重试次数 / 总执行次数 | < 10% | > 20% |
