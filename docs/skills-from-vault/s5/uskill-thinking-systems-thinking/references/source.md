# 🎯 目标

运用系统思维方法论，识别复杂系统中的反馈回路、杠杆点和系统原型，为组织问题分析、政策评估、环境系统理解和产品生态系统设计提供结构化的系统诊断与干预方案。

**核心价值**：将隐性的系统结构显性化，避免线性思维导致的政策副作用，发现高杠杆干预点。

**适用场景**：组织效率瓶颈诊断、公共政策副作用预测、产品生态系统涌现行为分析、环境与经济系统耦合建模。

## 📥 输入

## 参数表格

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `problem_description` | string | 是 | - | 需要分析的系统问题描述，越具体越好 |
| `system_boundary` | enum | 否 | "moderate" | 系统边界范围：narrow / moderate / broad |
| `time_horizon` | string | 否 | "3年" | 分析的时间跨度 |
| `stakeholders` | list | 否 | [] | 已知的利益相关方列表 |
| `existing_data` | object | 否 | {} | 已有的数据、指标或历史信息 |
| `intervention_intent` | string | 否 | "" | 用户期望的干预方向（可选） |
| `output_format` | enum | 否 | "full" | 输出详细度：summary / standard / full |

## 输入约束

- `problem_description` 长度不少于 20 字，必须包含至少一个可观测的现象或症状
- `system_boundary` 选择 broad 时，必须提供 `stakeholders` 列表
- `time_horizon` 格式为数字+时间单位（天/周/月/年）
- 若 `existing_data` 包含时序数据，优先用于识别趋势和周期

## 📋 执行步骤

## Step 1: 问题边界界定

**输入**：`problem_description` + `system_boundary`

**动作**：
1. 解析问题描述，提取核心症状和可观测现象
2. 根据 `system_boundary` 确定分析范围
3. 识别系统的内外边界

**输出**：系统边界声明文档

**检查点**：问题描述是否足够具体？边界是否合理？

**IF** `problem_description` 过于模糊（< 20 字）→ **THEN** 要求用户补充细节，列出 3 个引导性问题
**IF** `system_boundary` = broad 但 `stakeholders` 为空 → **THEN** 先执行利益相关方识别步骤
**ELSE** 进入 Step 2

---

## Step 2: 变量识别与分类

**输入**：系统边界声明

**动作**：
1. 识别系统中的关键变量
2. 将变量分类为存量（stock）、流量（flow）、辅助变量（auxiliary）
3. 标注哪些变量可测量、哪些需要代理指标

**输出**：变量清单 + 分类表

**检查点**：
- 存量和流量是否配对？
- 是否遗漏关键变量？
- 变量命名是否清晰无歧义？

**IF** 变量数量 > 20 → **THEN** 按子系统分组，优先保留与问题直接相关的变量
**IF** 关键变量无法测量 → **THEN** 设计代理指标，标注测量不确定性
**ELSE** 进入 Step 3

---

## Step 3: 因果关系建模

**输入**：变量清单

**动作**：
1. 建立变量间的因果关系（A → B，标注极性 +/-）
2. 识别时间延迟（delay）的位置
3. 构建因果循环图（CLD）

**输出**：因果循环图 + 关系矩阵

**检查点**：
- 因果链是否闭合形成回路？
- 极性标注是否一致？
- 延迟位置是否合理？

**IF** 发现孤立变量（无因果连接）→ **THEN** 重新审视该变量的必要性，或补充遗漏的因果关系
**IF** 因果关系方向存疑 → **THEN** 标注为"待验证"，提供两种可能方向的分析
**ELSE** 进入 Step 4

---

## Step 4: 反馈回路与系统原型识别

**输入**：因果循环图

**动作**：
1. 提取所有反馈回路（增强回路 R、调节回路 B）
2. 识别系统原型（archetypes）
3. 分析回路间的竞争与协同关系

**输出**：反馈回路清单 + 系统原型匹配结果

**检查点**：
- 每个回路是否包含至少 3 个变量？
- 原型匹配的置信度是否合理？
- 是否存在未被回路覆盖的重要变量？

**IF** 无法识别任何反馈回路 → **THEN** 回退到 Step 3 检查因果关系是否遗漏
**IF** 多个原型高度匹配 → **THEN** 选择与问题最相关的 2-3 个进行深入分析
**ELSE** 进入 Step 5

---

## Step 5: 杠杆点分析

**输入**：反馈回路 + 系统原型

**动作**：
1. 应用 Meadows 杠杆点框架（12 层级）
2. 评估每个潜在干预点的影响潜力和实施难度
3. 排序杠杆点优先级

**输出**：杠杆点清单（含影响评估）

**检查点**：
- 杠杆点是否位于回路的关键节点？
- 影响评估是否考虑了时间维度？
- 是否识别了高杠杆但低难度的"速赢"点？

**IF** 所有杠杆点都是高难度 → **THEN** 寻找参数层或缓冲层的次优但可行干预点
**IF** 用户提供了 `intervention_intent` → **THEN** 优先评估与意图匹配的杠杆点
**ELSE** 进入 Step 6

---

## Step 6: 干预方案设计

**输入**：杠杆点清单 + 用户意图

**动作**：
1. 针对 Top 3 杠杆点设计具体干预方案
2. 分析每个方案的二阶效应和副作用
3. 设计监控指标和预警机制

**输出**：干预方案集 + 监控框架

**检查点**：
- 方案是否直接作用于杠杆点？
- 副作用是否可接受？
- 监控指标是否可操作？

**IF** 干预方案可能触发系统原型的"转移负担"模式 → **THEN** 警告用户并提供替代方案
**IF** 副作用风险高于预期收益 → **THEN** 标记该方案为"高风险"，建议人工评审
**ELSE** 进入 Step 7

---

## Step 7: 综合输出与文档化

**输入**：所有分析结果

**动作**：
1. 汇总系统图谱、原型匹配、杠杆点和干预方案
2. 生成结构化 JSON 输出
3. 标注 `mental_models_applied`（使用的思维模型）

**输出**：完整分析报告

**检查点**：
- 输出是否符合 JSON Schema？
- 是否覆盖所有必填字段？
- `mental_models_applied` 是否准确列出使用的模型？

**IF** 输出不完整 → **THEN** 补充缺失部分，标注"数据不足"的字段
**ELSE** 输出最终结果

## ⚠️ 边界约束

## 硬性约束

| # | 约束 | 说明 |
|---|------|------|
| 1 | 不做因果关系的因果推断 | 系统思维识别相关性和回路，不做 A 导致 B 的统计证明 |
| 2 | 不替代专业领域知识 | 系统分析需要领域专家验证变量选择和因果假设 |
| 3 | 不预测精确数值 | 系统动力学输出定性趋势，不输出精确预测值 |
| 4 | 不忽略时间维度 | 所有反馈回路必须标注延迟特征 |
| 5 | 不提供单一最优解 | 系统问题通常有多个可行干预路径 |

## 软性约束

- 优先使用用户已有数据构建模型
- 术语选择应匹配用户的专业背景
- 复杂系统图优先以文字描述 + mermaid 语法呈现

## 人工兜底点

- 变量选择和因果假设需要领域专家确认
- 杠杆点评估需要结合组织实际执行力
- 干预方案需要利益相关方评审

## ⚠️ 异常处理

## 异常表格

| 异常代码 | 触发条件 | 处理方式 | 严重级别 |
|----------|----------|----------|----------|
| ERR-BOUNDARY | 问题描述模糊，无法确定系统边界 | 返回引导性问题清单，要求用户补充 | high |
| ERR-VAR-EMPTY | 无法识别出任何系统变量 | 提供变量识别模板，建议从利益相关方视角切入 | high |
| ERR-LOOP-0 | 因果循环图中无反馈回路 | 回退检查因果关系，提示可能遗漏关键连接 | high |
| ERR-ARCH-0 | 无法匹配任何系统原型 | 标注为"新型组合"，仍完成杠杆点分析 | medium |
| ERR-LEVERAGE-0 | 所有杠杆点实施难度极高 | 降级为参数层干预建议，标注为次优方案 | medium |
| WARN-DELAY | 关键回路延迟信息缺失 | 标注为"延迟未知"，建议用户补充时间数据 | low |
| WARN-MEASURE | 关键变量无法直接测量 | 提供代理指标建议，标注测量不确定性 | low |

## 降级策略

1. **数据不足降级**：仅输出变量识别和初步因果关系，跳过原型匹配
2. **边界模糊降级**：输出 narrow 范围的核心回路分析，建议用户扩展
3. **原型不匹配降级**：输出通用杠杆点框架，不进行原型标注

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
