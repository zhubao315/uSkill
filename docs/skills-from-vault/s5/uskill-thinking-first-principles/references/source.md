# 🎯 目标

运用第一性原理思维方法，从基本事实和不可进一步分解的前提出发进行推理，拆解隐含假设，重构对问题的认知框架，为创新思考、问题根因分析、技术方案评估和商业模型设计提供根本性的洞察。

**核心价值**：打破类比思维的限制，从物理现实和基本逻辑出发发现真正创新的可能性。

**适用场景**：颠覆式创新构思、技术路线根本性评估、商业模型底层逻辑验证、复杂问题的根因分析。

## 📥 输入

## 参数表格

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `problem_or_claim` | string | 是 | - | 需要分析的问题、观点或"常识性"论断 |
| `domain` | string | 否 | "" | 所属领域（技术/商业/社会/个人） |
| `current_approach` | string | 否 | "" | 当前主流做法或已有方案 |
| `depth_level` | enum | 否 | "standard" | 分析深度：surface / standard / deep |
| `goal` | string | 否 | "" | 用户期望达成的目标或解决的问题 |
| `known_facts` | list | 否 | [] | 已知的基本事实或约束条件 |
| `output_format` | enum | 否 | "full" | 输出详细度：summary / standard / full |

## 输入约束

- `problem_or_claim` 必须是可以被质疑和拆解的具体论断或问题
- `depth_level` = deep 时，要求提供 `known_facts` 至少 3 条
- `current_approach` 为空时，系统将先识别主流做法再进行拆解
- 不支持纯主观偏好类问题（如"什么是最好的颜色"）

## 📋 执行步骤

## Step 1: 问题澄清与边界界定

**输入**：`problem_or_claim` + `domain`

**动作**：
1. 精确复述用户的问题或论断
2. 界定问题的领域范围
3. 识别当前主流做法（若 `current_approach` 为空）
4. 明确分析的目标和约束

**输出**：问题定义文档

**检查点**：问题是否可被拆解？是否涉及事实判断而非纯价值判断？

**IF** `problem_or_claim` 是纯主观偏好 → **THEN** 返回提示：第一性原理适用于事实和逻辑问题，建议换用价值判断框架
**IF** `domain` 未指定 → **THEN** 从问题描述中推断领域，标注"领域推断"供用户确认
**ELSE** 进入 Step 2

---

## Step 2: 假设识别与分类

**输入**：问题定义

**动作**：
1. 列出所有隐含的假设（explicit / implicit / unconscious）
2. 对每个假设进行分类
3. 初步评估假设的有效性

**输出**：假设清单 + 分类表

**检查点**：
- 是否识别出"无人质疑"的隐含假设？
- 假设分类是否准确？
- 是否遗漏了关于时间、空间、资源的隐含假设？

**IF** 假设数量 < 3 → **THEN** 可能拆解不够深入，提示用户增加分析深度或补充背景信息
**IF** 发现 unconscious 类假设 → **THEN** 特别标注，这些通常是创新的最大障碍
**ELSE** 进入 Step 3

---

## Step 3: 基本事实提取

**输入**：假设清单 + `known_facts`

**动作**：
1. 从假设中区分出"事实"和"推断"
2. 补充已知的基本事实（用户提供 + 领域常识）
3. 评估每个事实的确定性和可测试性
4. 确定不可再分的基本前提

**输出**：基本事实清单

**检查点**：
- 每个"事实"是否真的不可再分？
- 是否区分了物理事实和社会建构？
- 事实的来源是否可靠？

**IF** 无法确定某些"事实"的可靠性 → **THEN** 标注为"待验证事实"，提供验证方法建议
**IF** `known_facts` 与领域常识冲突 → **THEN** 标注冲突，要求用户澄清
**ELSE** 进入 Step 4

---

## Step 4: 假设拆解与验证

**输入**：假设清单 + 基本事实

**动作**：
1. 用基本事实逐一检验每个假设
2. 对可测试的假设设计验证方法
3. 对不可测试的假设评估其逻辑一致性
4. 标注假设的有效性等级

**输出**：假设验证报告

**检查点**：
- 拆解是否到达"不可再分"的层级？
- 验证方法是否可操作？
- 是否发现了被广泛接受但实际无效的假设？

**IF** `depth_level` = deep → **THEN** 对每个假设进行三层追问（为什么→为什么→为什么）
**IF** 发现核心假设无效 → **THEN** 这是重大发现，特别标注并展开分析其影响
**ELSE** 进入 Step 5

---

## Step 5: 推理链条重构

**输入**：基本事实 + 验证后的假设

**动作**：
1. 从基本事实出发，逐层构建推理链条
2. 每一步标注前提、推理过程和结论
3. 检查每一步的逻辑间隙（gap_check）
4. 确保推理链条完整且无跳跃

**输出**：重构推理链条

**检查点**：
- 每一步推理是否都有充分的前提支撑？
- 是否存在逻辑跳跃或循环论证？
- 推理链条是否可被独立验证？

**IF** 推理链条出现断裂 → **THEN** 补充缺失的中间步骤，或标注"需要额外前提"
**IF** 推理得出与常识相反的结论 → **THEN** 回溯检查，确认不是推理错误而是真实洞察
**ELSE** 进入 Step 6

---

## Step 6: 洞察生成与方案重构

**输入**：重构推理链条 + 拆解后的假设

**动作**：
1. 识别推理链条带来的新洞察
2. 基于新洞察重构解决方案或理解框架
3. 评估重构方案的优势和挑战
4. 确定需要进一步验证的领域

**输出**：新洞察清单 + 重构方案

**检查点**：
- 洞察是否真正源于基本事实推理？
- 重构方案是否具有可操作性？
- 是否遗漏了重要的约束条件？

**IF** 重构方案过于理想化 → **THEN** 标注实施挑战，提供分阶段落地建议
**IF** 洞察与 `goal` 不相关 → **THEN** 过滤不相关洞察，聚焦于目标导向的分析
**ELSE** 进入 Step 7

---

## Step 7: 综合输出与文档化

**输入**：所有分析结果

**动作**：
1. 汇总假设拆解、基本事实、推理链条和重构方案
2. 生成结构化 JSON 输出
3. 标注 `thinking_models_applied`

**输出**：完整分析报告

**检查点**：
- 输出是否符合 JSON Schema？
- 推理链条是否可追溯？
- 是否标注了所有不确定性？

**IF** 输出不完整 → **THEN** 补充缺失部分
**ELSE** 输出最终结果

## ⚠️ 边界约束

## 硬性约束

| # | 约束 | 说明 |
|---|------|------|
| 1 | 不替代领域专业知识 | 第一性原理提供思维框架，不替代具体领域的事实判断 |
| 2 | 不保证创新一定可行 | 从基本事实出发可能得出理论上正确但实践中不可行的方案 |
| 3 | 不适用于纯价值判断 | "什么是好的"属于价值范畴，不是第一性原理的适用领域 |
| 4 | 不做概率预测 | 第一性原理分析定性可能性，不预测具体概率 |
| 5 | 不忽视类比思维的价值 | 拆解假设不等于否定所有类比，只质疑不合理的类比 |

## 软性约束

- 优先选择可测试的事实作为基本前提
- 推理链条应尽可能简洁
- 重构方案应考虑现实约束

## 人工兜底点

- 基本事实的选择需要领域专家确认
- 假设的有效性评估需要实证数据支持
- 重构方案的可行性需要实践验证

## ⚠️ 异常处理

## 异常表格

| 异常代码 | 触发条件 | 处理方式 | 严重级别 |
|----------|----------|----------|----------|
| ERR-SUBJECTIVE | 问题属于纯主观价值判断 | 返回提示，建议换用价值判断框架 | high |
| ERR-NO-FACTS | 无法确定任何基本事实 | 标注为"假设性分析"，所有推理标记为待验证 | high |
| ERR-CIRCULAR | 推理出现循环论证 | 回溯定位循环起点，重新选择前提 | high |
| ERR-DEEP-INSUFFICIENT | deep 模式下假设拆解不够深入 | 补充追问链，标注"可能仍有未拆解假设" | medium |
| ERR-CONFLICT | 用户提供的事实与领域常识冲突 | 标注冲突点，要求用户澄清 | medium |
| WARN-UNVERIFIABLE | 关键事实无法验证 | 标注为"逻辑前提"，提供可能的验证路径 | low |
| WARN-IDEALIZED | 重构方案过于理想化 | 标注实施挑战，建议增加约束条件 | low |

## 降级策略

1. **事实不足降级**：标注所有推理为"基于假设的推理"，降低置信度
2. **深度不足降级**：仅完成表面假设拆解，建议用户后续深入
3. **领域未知降级**：使用通用推理框架，标注领域知识缺口

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
