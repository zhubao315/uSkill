# [[数据驱动决策分析]]

## 🎯 目标

> 将原始数据转化为可执行的决策洞察，而非堆砌数字的报表。

**核心价值**：数据报告最常见的失败是「给了 100 个数字，但没人知道该做什么」。本 Skill 确保每份报告都以行动建议结尾。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `data_source` | string | ✅ | — | 数据源描述 |
| `report_type` | enum | ❌ | `"executive"` | 类型：`executive`（高管摘要）/ `operational`（运营日报）/ `strategic`（战略分析）/ `ad_hoc`（临时分析） |
| `audience` | enum | ❌ | `"leadership"` | 受众：`leadership`（管理层）/ `team`（团队）/ `external`（外部） |
| `time_range` | enum | ❌ | `"monthly"` | 分析周期 |

## 📤 输出

```json
{
  "report": {
    "headline": "string — 一句话核心结论",
    "key_metrics": [{"metric": "string", "value": "string", "change": "string", "trend": "string"}],
    "insights": ["string — 数据洞察（带原因分析）"],
    "recommendations": [{"action": "string", "impact": "string", "effort": "string"}]
  },
  "dashboard": {
    "charts": ["string — 图表描述"],
    "filters": ["string — 筛选维度"]
  }
}
```

## 📋 执行步骤

### Step 1: 数据准备
1. **数据提取** — 从数据源获取所需数据
2. **质量检查** — 检查缺失值/异常值/口径一致性
3. **指标定义** — 明确每个指标的计算口径
4. **检查点**：✅ 数据是否完整？指标口径是否明确？

### Step 2: 分析与洞察
1. **趋势分析** — 同比/环比变化
2. **对比分析** — 与目标/行业/竞品对比
3. **归因分析** — 变化的原因是什么
4. **预测** — 基于趋势预判未来走向
5. **检查点**：✅ 分析是否有归因？是否有预测？

### Step 3: 报告撰写
1. **金字塔结构** — 结论先行 → 数据支撑 → 行动建议
2. **可视化** — 图表 > 数字，每页一个核心信息
3. **语言精炼** — 删减不影响决策的文字
4. **检查点**：✅ 结论是否在第一页？可视化是否清晰？

### Step 4: 行动建议
1. **具体化** — 每个建议有明确的「谁做什么」
2. **优先级** — 按影响力排序
3. **资源评估** — 每个建议的投入和预期产出
4. **检查点**：✅ 建议是否具体可执行？优先级是否明确？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 数据缺失 | 关键指标无数据 | 标记数据缺口，基于已有数据估算 |
| 口径不一致 | 不同系统数据矛盾 | 统一口径定义，标注数据来源 |
| 分析周期短 | 数据量不足 | 扩大时间范围或降级分析深度 |

## 💬 沟通风格

- **结论先行**：第一页就说「所以呢」
- **图表说话**：能用图表不用表格，能用表格不用文字
- **行动导向**：不只说「是什么」，更要说「该做什么」

## 📝 自检清单

- [ ] 每个指标是否有对比基准？

- [ ] 行动建议是否具体可执行？
- [ ] 图表是否清晰易懂？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）

- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时

- 不跳过验证步骤

- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
