# Three Stage Reasoning（三段式推理）

## 🎯 目标
> 通过大前提、小前提、结论的三段结构，从普遍规律出发对具体案例进行严格逻辑推导，确保思维严密、结论可靠。

## 📥 输入

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `context` | string | ✅ | 需要分析的具体情境或问题描述 |
| `goal` | string | ❌ | 推理的目标——想得出什么结论或做出什么判断 |
| `known_facts` | string[] | ❌ | 已知的具体事实列表（用于构建小前提） |
| `candidate_rules` | string[] | ❌ | 候选的普遍规律或经验法则（用于构建大前提） |
| `rigor_level` | enum | ❌ | 严格程度：`quick`（快速检验）/ `standard`（标准流程）/ `strict`（严格审计），默认 `standard` |

## 📋 执行步骤

### 阶段一：确立大前提（普遍规律）

1. **识别候选规律** — 从问题域中提取可能适用的普遍规律、科学定律、统计规律或经验法则
2. **验证前提真实性** — 对每个候选大前提进行证据审查：
   - 是否有充分的科学/数据/经验支持？
   - 是否存在已知例外或边界条件？
   - 该规律的适用范围是什么？
3. **明确前提范围** — 精确界定大前提的适用边界，避免过度泛化
   - ❌ "投资都能赚钱" → 过度泛化
   - ✅ "长期定投宽基指数基金，在20年周期内大概率获得正收益" → 精确范围

### 阶段二：匹配小前提（具体事实）

4. **客观描述事实** — 用中性、精确的语言描述具体情境，剥离情感与预设立场
   - ❌ "小王工作很辛苦，天天对着电脑"
   - ✅ "小王日均屏幕使用时间为8.5小时"
5. **验证相关性** — 确认小前提中的具体案例确实属于大前提的适用范围
6. **检查中项周延** — 确认连接大小前提的"中项"在至少一个前提中涵盖全部范围
   - ❌ "部分学生喜欢数学" + "王明是学生" → 中项"学生"未周延
   - ✅ "所有学生都要考试" + "王明是学生" → 中项"学生"已周延

### 阶段三：推导结论

7. **构建逻辑桥梁** — 严密连接大前提与小前提，确保推理链无跳跃
8. **严格限定结论范围** — 结论绝不超越前提所设定的边界
   - 从"有些X是Y"只能推出"某些X是Y"，不能推出"所有X是Y"
9. **表达结论强度** — 根据前提的确定性程度标注结论的置信度
   - `certain`：前提绝对可靠，结论必然成立
   - `probable`：前提有较强支持，结论很可能成立
   - `possible`：前提支持有限，结论仅为可能

### 阶段四：审计与验证

10. **逻辑结构审计** — 检查推理形式是否有效（独立于前提真假）
11. **五大陷阱扫描** — 系统检查以下常见谬误：
    | 谬误类型 | 检测方法 |
    |----------|---------|
    | 滑坡谬误 | 检查因果链中每一环是否有独立证据 |
    | 肯定后件 | 检查是否将"若A则B"反推为"若B则A" |
    | 否定前件 | 检查是否将"若A则B"误推为"若非A则非B" |
    | 仓促概括 | 检查样本量是否足以支撑普遍结论 |
    | 伪两难困境 | 检查是否存在被忽略的第三种以上可能性 |
12. **生成替代解读** — 提供其他可能的推理路径或结论

## ⚠️ 异常处理

| 异常 | 处理 |
|------|------|
| 大前提无法找到可靠证据 | 标记为 `unverifiable`，降低结论置信度至 `possible`，建议收集更多数据 |
| 小前提事实不清 | 列出需要澄清的具体事实点，暂缓推理 |
| 中项不周延 | 明确指出逻辑漏洞，拒绝给出确定性结论 |
| 结论超出前提范围 | 自动收窄结论范围，或警告用户并提供两种版本（严格/宽松） |
| 检测到逻辑谬误 | 标注谬误类型、位置，并提供修正后的推理路径 |
| 多个大前提冲突 | 分别推理，对比结论，提示用户选择或综合 |
| 情境过于复杂无法简化为三段 | 建议拆解为多个子问题，逐段推理后综合 |

## 💡 实战示例

### 示例 1：投资决策分析

```
输入:
  context: "考虑是否投资某新能源公司股票"
  known_facts: ["该公司过去3年营收增长40%+", "新能源政策持续利好", "当前PE为80倍"]
  candidate_rules: ["高PE股票在利率上行期容易回调", "政策支持行业的龙头公司长期增长概率高"]

推理过程:
  大前提: PE超过行业均值2倍的股票，在利率上行阶段有较高回调概率
  小前提: 该公司PE为80倍，远超新能源行业均值35倍，且当前处于利率上行期
  中项: "PE超行业均值2倍的股票"
  结论: 该公司短期存在较高的估值回调风险

  ⚡ 补充推理:
  大前提: 政策支持行业的龙头企业，长期（5年+）增长概率较高
  小前提: 该公司是新能源龙头，政策持续支持
  结论: 长期配置价值存在，建议分批建仓而非一次性重仓

输出:
  综合建议: 短期有回调风险，长期有价值。建议等待估值回落后再分批建仓。
```

### 示例 2：日常判断检验

```
输入:
  context: "朋友说'这家餐厅大众点评4.8分，肯定好吃'"

拆解隐含推理:
  大前提: 大众点评高分餐厅都好吃（隐含）
  小前提: 这家餐厅4.8分
  结论: 这家餐厅好吃

审计:
  ⚠️ 大前提存疑：高分可能来自刷单、新店评分样本小、口味因人而异
  ⚠️ 仓促概括风险：4.8分是相关信号，但不是充分条件
  ✅ 修正结论: 这家餐厅大概率不差，但不能保证"肯定好吃"，建议结合评论内容判断
```

### 示例 3：法律推理

```
输入:
  context: "某员工因旷工3天被公司辞退，是否合法？"

推理:
  大前提: 《劳动合同法》规定，严重违反用人单位规章制度的，用人单位可以解除劳动合同
  小前提: 公司规章制度明确规定"连续旷工3天视为严重违纪"，且该制度经过民主程序制定并向员工公示
  结论: 公司辞退行为合法

  ⚠️ 但需检查:
  - 规章制度是否确实经过合法程序？
  - 是否向该员工公示过？
  - 旷工是否有正当理由（如突发疾病）？
  若任一条件不满足，结论可能翻转。
```

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

- 检查常见错误

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
