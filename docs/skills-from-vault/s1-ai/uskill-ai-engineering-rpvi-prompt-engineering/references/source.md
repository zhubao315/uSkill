
# RPVI提示词工程

> 结构化提示词设计框架——通过 Role/Project/Vision/Implementation 四要素提升 LLM 输出质量。

## 框架详解

```
R: 你是一位 [角色]，擅长 [能力]
P: 当前项目背景：[技术栈/约束/现状]
V: 目标：[要实现什么]
I: 实现要求：[具体规范/格式/示例]
```

## 为什么有效

- **角色设定**激活 LLM 的相关知识域
- **项目上下文**减少幻觉和不相关输出
- **目标明确**避免 LLM 自由发挥偏离方向
- **实现约束**保证输出可直接使用

## 进阶技巧

| 技巧 | 说明 |
|------|------|
| **Few-shot 示例** | 给 1-2 个输入输出示例 |
| **Chain of Thought** | 要求 LLM 先思考再输出 |
| **输出格式约束** | 指定 JSON/Markdown/代码块 |
| **负面指令** | 明确「不要做什么」 |

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## ⚠️ 异常处理

| 异常类型 | 触发条件 | 处理方式 |
|---------|---------|---------|
| 输入缺失 | 必填参数为空 | 提示用户补充输入 |
| 格式错误 | 输入格式不符合要求 | 给出格式示例 + 重新输入 |
| 执行超时 | 单次执行超过阈值 | 降级处理 + 记录日志 |
| 结果异常 | 输出明显不合理 | 标记异常 + 人工复核 |

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📊 执行规范

**输入验证**：
- 必填参数检查：缺失时返回明确错误提示
- 类型校验：参数类型不匹配时返回类型错误
- 范围校验：数值超出合理范围时返回范围提示
- 格式校验：不符合预期格式时给出格式示例

**执行约束**：
- 单次执行超时：30 秒（可配置）
- 最大重试次数：3 次
- 并发限制：同一资源不并发写入
- 幂等性：相同输入产生相同输出

**输出规范**：
- 格式：JSON 结构化输出
- 必含字段：status/message/data/timestamp
- 错误输出：error_code/error_message/suggestion
- 日志：执行过程关键节点记录

## 📈 质量指标

| 指标 | 计算方式 | 目标 | 告警阈值 |
|------|---------|:----:|:--------:|
| 成功率 | 成功次数 / 总执行次数 | ≥ 95% | < 90% |
| 平均耗时 | 总耗时 / 执行次数 | < 10s | > 30s |
| 错误率 | 错误次数 / 总执行次数 | < 5% | > 10% |
| 重试率 | 重试次数 / 总执行次数 | < 10% | > 20% |
