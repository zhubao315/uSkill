
# 软件测试每日任务

每日 3 条实操待办，融合软件测试、自动化测试、LLM 测试三大方向。每条包含 **动作 → 目标 → 产出**，聚焦当天可完成的小目标。

## Day 1 · 2026-05-18

### Task 1

> 用 Playwright 录制一个 LLM 聊天页面的交互脚本（输入 prompt → 等待流式响应），并断言关键元素加载

**动作**：打开任意 LLM 聊天界面（如 ChatGPT / Claude / 本地部署模型），用 `playwright codegen` 录制一次完整问答交互并导出脚本；添加 `expect` 断言检查欢迎消息或响应容器出现。

**目标**：掌握 Playwright Codegen 录制 + 基础断言写法，验证 LLM 流式 UI 的可测试性。

**产出**：一个可独立运行的 `test_chat.spec.ts` 脚本。

### Task 2

> 用 Pytest + pytest-xdist 对一个已有接口测试集做并行化改造，压测 10 次记录耗时

**动作**：选一个本地或公开 REST API（如 JSONPlaceholder），写 5 条接口测试用例（GET/POST）；加 `@pytest.mark.parametrize` 参数化；用 `pytest -n auto` 开启并行执行，对比串行/并行耗时。

**目标**：掌握 pytest 参数化 + 并行执行配置，量化自动化执行效率提升。

**产出**：一个 `test_api_parallel.py` + 串并行耗时对比数据。

### Task 3

> 用 LLM 对一个历史缺陷报告做根因分类 + 生成回归测试用例

**动作**：手动准备 1 条真实或模拟的缺陷报告（含堆栈、日志、环境信息）；用 LLM API 提取关键根因标签（如 NPE/并发/数据不一致），并让 LLM 基于缺陷描述生成 3 条回归测试用例；人工评审用例有效性。

**目标**：实践 LLM 辅助缺陷分析 + 测试用例生成，评估 LLM 输出质量。

**产出**：一份缺陷分析报告（含 LLM 根因标签 + 回归用例 + 人工评审结论）。

## 使用说明

- 每天选 3 条执行，总时间控制在 **2~4 小时**
- 如某天被其他事务占用，顺延即可
- 每完成一条，在 `[ ]` 前加 `[x]` 标记
- 遇到阻碍或发现更好的选题，随时替换


#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

**合规校验**：
- [ ] 未违反硬性约束

#### 🔄 迭代触发条件

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

```
你是一位资深软件测试工程师，精通测试用例设计、自动化测试和质量保障体系。请根据以下输入规划每日测试任务：
```

## 🎯 技能概述

> 本技能提供 通用 领域的标准化操作流程，帮助用户高效完成相关任务。

**核心价值**：将复杂操作标准化为可重复执行的步骤，降低出错率，提升效率。

**适用场景**：
1. 日常操作执行
2. 新手快速上手
3. 质量一致性保证

## 🧪 Self-Play 测试用例

|---|------|------|----------|--------|

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
