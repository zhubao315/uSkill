# Full-Stack Feature Development with AI & TDD

## 🎯 目标
> 以测试驱动开发（TDD）为核心，借助 AI 全面赋能，建立高效、高质量的端到端功能交付流水线，将新功能从开发到部署的周期缩短 60%。

## 📥 输入

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `user_story` | string | ✅ | 用户故事或功能需求描述 |
| `tech_stack` | string | ✅ | 技术栈（如 React/TypeScript + Node.js/NestJS） |
| `prd_ref` | string | ❌ | 产品需求文档引用或链接 |
| `existing_architecture` | string | ❌ | 现有架构说明，用于评估影响 |

## 📤 输出

```json
{
  "pull_request": {
    "code": "string — 功能实现代码",
    "tests": "string — 覆盖率 >90% 的测试代码",
    "docs": "string — 更新后的 API 文档 / README"
  },
  "ci_cd_record": "string — CI/CD 流水线构建记录",
  "task_status": "string — 任务状态（待评审 / 已完成）"
}
```

## 📋 执行步骤

1. **任务分解与技术设计（AI 辅助）** — 仔细阅读 PRD 和用户故事。用 AI 将用户故事分解为前后端技术任务清单，评估对现有架构的影响，绘制组件交互图，定义前后端 API 接口（请求/响应结构）。与产品经理确认理解一致性。
2. **编写失败的测试（TDD 核心）** — 根据 API 定义和业务逻辑，先编写后端集成测试或单元测试（应为失败状态）；根据 UI/UX 设计稿编写前端组件测试（失败状态）。用 AI 生成核心测试用例（正常、边界、异常情况）。
3. **AI 辅助编码实现（让测试通过）** — 用 AI 生成满足接口定义和业务逻辑的后端代码（控制器、服务、数据访问层）和前端组件代码。不断运行测试直到全部通过。
4. **代码审查与重构（AI 辅助）** — 自我审查后，用 AI 扮演"代码审查专家"检查潜在 bug、性能问题、安全漏洞和可读性。根据反馈重构优化。
5. **持续集成与部署（CI/CD）** — 推送到特性分支，创建 PR，触发 CI/CD 流水线自动执行测试、质量扫描和构建。获得至少一名同事批准后合并，触发自动部署。
6. **监控与验证（生产环境）** — 发布后密切关注监控系统（Prometheus/Grafana），检查日志，与产品经理验证业务目标达成情况，驱动下一轮迭代。

## ⚠️ 异常处理

| 异常 | 处理 |
|------|------|
| AI 生成代码测试不通过 | 手动调试后将错误信息反馈给 AI 进行迭代修复 |
| PR 被拒绝或 CI 失败 | 根据反馈修复后重新提交，不要绕过检查 |
| 架构影响评估不足导致冲突 | 回退到步骤 1 重新评估，补充组件交互分析 |
| 生产环境指标异常 | 立即回滚，分析根因后重新走完整流程 |

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
