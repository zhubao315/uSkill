# Microservice Decomposition Decision

> **角色**: 系统架构师 | **核心工具**: AI大模型, 架构分析工具, DDD建模 | **效率目标**: 结构化微服务拆分决策，降低架构演进风险

## 🎯 目标

构建从**单体到微服务**的系统化拆分决策框架，基于领域驱动设计(DDD)识别业务边界，通过量化评估确定拆分优先级，确保架构演进有序可控。

**适用场景**:
1. **单体应用拆分** — 现有单体系统面临扩展瓶颈，需要逐步拆分为微服务
2. **新系统架构设计** — 从零设计微服务架构，确定服务边界
3. **现有微服务重构** — 已有微服务架构但边界不合理，需要重新划分

## 📋 执行步骤

### 阶段一：现状评估与拆分必要性判断

1. **架构痛点诊断** — 分析当前架构的核心问题：
   - 部署耦合：改一行代码需要部署整个系统？
   - 扩展瓶颈：无法对高负载模块独立扩容？
   - 团队瓶颈：多团队频繁代码冲突？
   - 技术栈僵化：无法为特定场景选择最优技术？
2. **拆分必要性评分** — 评估是否真正需要微服务（警惕"简历驱动开发"）
3. **确定拆分约束** — 明确团队规模、时间窗口、基础设施成熟度

### 阶段二：领域建模与边界识别

4. **事件风暴 (Event Storming)** — 组织跨职能工作坊，梳理业务领域事件
5. **识别限界上下文** — 基于DDD方法划分业务边界：
   - **核心域**: 企业核心竞争力所在，投入最多资源
   - **支撑域**: 为核心域提供支撑，可自建或外购
   - **通用域**: 通用能力（用户、权限、通知），可直接购买
6. **绘制上下文映射** — 定义限界上下文之间的关系和交互模式
7. **验证边界合理性** — 检查：每个上下文是否可以独立演进？数据归属是否清晰？

### 阶段三：服务拆分方案设计

8. **确定拆分策略**:
   - **绞杀者模式 (Strangler Fig)**: 逐步将功能从单体迁移到新服务
   - **分支 by 抽取 (Branch by Abstraction)**: 先抽象接口，再替换实现
   - **并行运行 (Parallel Run)**: 新旧系统并行，逐步切换流量
9. **服务粒度评估** — 使用量化标准：
   - 单个服务代码量 < 5万行
   - 团队1个披萨团队（5-8人）可以完全拥有
   - 服务可以独立部署、独立扩缩
10. **定义服务契约** — 确定API规范、事件格式、数据所有权

### 阶段四：迁移路线图制定

11. **拆分优先级排序** — 按以下维度评分：
    - 业务价值/痛点缓解度
    - 技术可行性/风险
    - 团队能力/学习曲线
12. **制定分阶段路线图** — 每个阶段明确服务列表、时间估算、里程碑
13. **基础设施规划** — 确定所需的基础设施组件（服务网格、配置中心、链路追踪等）
14. **风险评估与缓解** — 识别技术风险和组织风险，制定缓解措施

## ✅ 检查清单

- [ ] 是否进行了领域建模（事件风暴/领域分析）
- [ ] 每个服务的数据所有权是否明确
- [ ] 服务间通信方式是否确定（同步REST/gRPC vs 异步消息）
- [ ] 是否考虑了分布式事务处理方案
- [ ] 是否规划了服务发现、配置管理、监控告警
- [ ] 团队是否具备运维微服务的能力
- [ ] 迁移方案是否支持灰度发布和回滚
- [ ] 是否评估了不拆分的方案

## ⚠️ 常见陷阱

| 陷阱 | 说明 | 规避方法 |
|------|------|---------|
| 过早拆分 | 业务不成熟就拆微服务，增加复杂度 | 优先优化单体，实在不行再拆 |
| 分布式单体 | 拆了服务但仍然紧密耦合 | 严格遵守异步通信和独立部署 |
| 数据库共享 | 多个服务共享同一数据库 | 每个服务拥有独立数据存储 |
| 粒度过细 | 服务拆得太细，运维成本爆炸 | 遵循"两个披萨团队"原则 |
| 忽略组织架构 | 技术架构与组织架构不匹配 | 康威定律：架构应映射组织结构 |
| 缺少可观测性 | 分布式系统排障困难 | 必须先建设日志/指标/追踪三大支柱 |

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

```
你是一位资深微服务架构师，精通领域驱动设计（DDD）和服务拆分原则。请根据以下输入进行微服务拆分分析：
输入：现有系统架构描述、业务领域边界、团队组织结构、性能瓶颈点、数据耦合现状
要求：运用 DDD 方法识别限界上下文，评估拆分粒度与边界，设计服务间通信方式（同步/异步），分析数据拆分策略，识别拆分风险与实施路径
输出格式：限界上下文地图、微服务划分方案（含服务列表与职责定义）、服务间依赖关系图、数据拆分策略、分阶段实施路线图
```

**使用说明**：
- 替换方括号内的占位符为实际内容
- 根据具体场景调整要求部分
- 输出格式可根据需要修改

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
