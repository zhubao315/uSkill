# Draft AI Patent Application

## 🎯 目标
> 标准化撰写AI/软件领域高价值专利申请文件，将单个专利申请文件的撰写周期缩短60%，最大化保护范围和授权成功率。

## 📥 输入

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `technical_disclosure` | string | ✅ | 技术交底书：算法流程、系统架构、数据流等技术方案描述 |
| `innovation_points` | string[] | ❌ | 已识别的核心创新点列表（如未提供则由AI辅助提炼） |
| `prior_art` | string[] | ❌ | 已知的现有技术/对比文件（如未提供则由AI辅助检索） |
| `patent_type` | enum | ❌ | `method` / `system` / `medium` / `all`，默认 `all` |
| `target_jurisdiction` | enum | ❌ | `CN` / `US` / `EP` / `all`，默认 `CN` |
| `max_claims` | int | ❌ | 最大权利要求数，默认 10 |

## 📋 执行步骤

1. **提炼创新点** — 阅读 `technical_disclosure`，运用AI专家和架构师视角，提炼3-5个可能具有新颖性和创造性的核心技术特征
2. **生成检索策略** — 基于创新点制定多维度检索策略，包含中英文关键词、IPC/CPC分类号、布尔逻辑检索式
3. **执行现有技术检索** — 利用专利数据库检索3-5篇最相关的对比文件
4. **撰写专利性分析报告** — 逐一对比本发明与现有技术的区别，论证新颖性和创造性
5. **布局独立权利要求** — 围绕最小创新点撰写独立权利要求，覆盖方法、系统、介质等多种类型
6. **布局从属权利要求** — 从核心创新点向外围特征层层展开，构建进可攻退可守的立体保护体系
7. **撰写说明书** — 围绕权利要求书撰写背景技术、发明内容、具体实施方式、有益效果
8. **生成摘要与附图说明** — 提炼技术方案核心内容生成摘要，描述附图
9. **质量审查** — 检查术语一致性、权利要求支撑关系、格式合规性

## 🤖 内置提示词

### 创新点提炼
```
你是一位顶尖的AI领域专利代理师。请阅读我提供的技术交底书，并以专业的眼光，提炼出其中可能构成核心创新点的3-5个技术特征。请说明每个创新点解决了什么技术问题，并带来了什么有益效果。

技术交底书：{{technical_disclosure}}
```

### 检索策略生成
```
你是一位拥有15年经验的专利检索专家，尤其擅长AI和软件领域。基于以下核心创新点："{{innovation_points}}",请为我制定一个全面的检索策略。策略应包含：1. 至少5组中英文关键词（包含同义词和上位词）；2. 建议的IPC/CPC分类号；3. 至少3个布尔逻辑检索式；4. 建议检索的数据库列表（包含专利和非专利文献）。
```

### 专利性分析
```
你是一位专利审查员。我将提供我的发明创新点和一篇最相关的对比文件（现有技术）。请严格按照新颖性和创造性（三步法/T-S-M法）的标准，分析我的发明是否具备可专利性。请明确指出我的技术方案与对比文件的区别技术特征，并论述这些区别是否"显而易见"。

创新点：{{innovation_points}}
对比文件：{{prior_art}}
```

### 权利要求生成
```
你是一位精通AI算法专利撰写的专利代理师。我的发明的核心创新点是"{{innovation_points}}".请以此为核心，为我草拟一套层次清晰的权利要求书。要求包含：1. 至少1项保护范围最宽的方法独立权利要求；2. 至少1项对应的系统/装置独立权利要求；3. 至少5项从不同技术角度（如具体实现方式、参数优化、应用场景等）进一步限定的从属权利要求。
```

## ⚠️ 异常处理

| 异常 | 处理 |
|------|------|
| `technical_disclosure` 过于简略 | 返回提示：请补充技术方案的算法流程和系统架构描述 |
| 创新点缺乏新颖性 | 返回专利性分析报告，建议调整保护范围或放弃申请 |
| 权利要求语言不清晰 | 自动标记模糊术语，要求发明人澄清技术含义 |
| 说明书无法支撑权利要求 | 返回缺失支撑的具体权利要求编号和条款 |

## ✅ 自检清单

- [ ] 独立权利要求包含最少必要技术特征，保护范围最宽
- [ ] 从属权利要求对独立权利要求形成有效、有层次的限定
- [ ] 权利要求书语言清晰、无歧义
- [ ] 说明书至少描述一个完整的、可复现的实施例
- [ ] 权利要求中的每个技术术语在说明书中都有定义或解释
- [ ] 全文术语使用统一
- [ ] 附图标记在说明书中都有对应描述
- [ ] 格式符合目标国家/地区专利局的官方要求


#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
