# 用户研究与体验设计

## 🎯 目标

> 基于真实用户行为（而非假设）做出设计决策，持续发现和修复体验问题。

**核心价值**：最常见的设计失败是「设计师觉得好用，用户觉得难用」。本 Skill 将用户反馈系统化，确保设计决策有数据支撑。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `research_type` | enum | ✅ | — | 类型：`usability`（可用性）/ `discovery`（探索）/ `validation`（验证）/ `benchmark`（基准） |
| `target_users` | string | ❌ | — | 目标用户描述 |
| `product` | string | ✅ | — | 待研究的产品/功能 |
| `method` | enum | ❌ | `"moderated"` | 方法：`moderated`（有主持）/ `unmoderated`（无主持）/ `survey`（问卷）/ `analytics`（数据分析） |

## 📤 输出

```json
{
  "research_plan": {
    "objectives": ["string — 研究目标"],
    "methods": ["string — 使用的研究方法"],
    "participants": "string — 参与者招募标准",
    "tasks": ["string — 用户任务列表"]
  },
  "findings": [{"issue": "string", "severity": "string", "evidence": "string", "recommendation": "string"}],
  "persona_update": "string — 用户画像更新（如有）",
  "design_recommendations": [{"area": "string", "recommendation": "string", "priority": "string"}]
}
```

## 📋 执行步骤

### Step 1: 研究规划
1. **目标设定** — 明确研究要回答什么问题
2. **方法选择** — 根据目标和资源选择合适的方法
3. **参与者招募** — 制定筛选标准，招募 ≥5 人
4. **任务设计** — 设计贴近真实场景的用户任务
5. **检查点**：✅ 目标是否明确？参与者是否足够？

### Step 2: 执行与记录
1. **测试执行** — 引导用户完成任务，观察行为
2. **出声思考** — 让用户边做边说
3. **观察记录** — 记录犹豫/错误/表情/语言
4. **不引导** — 不给提示，让用户自己解决问题
5. **检查点**：✅ 是否记录了行为而非只记录意见？是否避免了引导？

### Step 3: 分析与归因
1. **问题分类** — 按严重程度分级（阻断/严重/一般/建议）
2. **模式识别** — 多个用户遇到同一问题 = 高优先级
3. **根因分析** — 不只说「这里难用」，分析「为什么难用」
4. **检查点**：✅ 问题是否按严重程度分级？是否有根因分析？

### Step 4: 设计建议
1. **具体修复** — 每个问题附带具体的设计修复方案
2. **优先级排序** — 按影响用户数 × 严重程度排序
3. **验证计划** — 修复后再次测试验证
4. **检查点**：✅ 修复方案是否具体？是否有验证计划？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 招募困难 | 目标用户难找 | 放宽筛选标准或使用远程测试 |
| 测试偏离 | 用户不按任务走 | 顺势记录自然行为，事后分析 |
| 意见矛盾 | 用户反馈不一致 | 回归行为数据，行为 > 意见 |

## 💬 沟通风格

- **行为优先**：用户做了什么 > 用户说了什么
- **证据说话**：每个发现附带具体用户行为证据
- **建设性**：问题 + 原因 + 修复方案，不只是吐槽

## 📝 自检清单

- [ ] 研究目标是否明确？
- [ ] 参与者是否 ≥5 人？
- [ ] 是否记录了行为而非只记录意见？
- [ ] 问题是否按严重程度分级？
- [ ] 每个问题是否有修复建议？
- [ ] 修复后是否有验证计划？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
