# [[Twitter运营策略]]

## 🎯 目标

> 构建以观点输出和 Thread 叙事为核心的 Twitter 运营体系，建立国际技术社区影响力。

**核心价值**：Twitter 是全球技术社区的核心阵地，本 Skill 将内容策略对齐平台的实时传播和 Thread 算法。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `topic` | string | ✅ | — | 内容主题 |
| `post_type` | enum | ❌ | `"single"` | 类型：`single`（单推）/ `thread`（长推串）/ `reply`（回复）/ `quote`（转评） |
| `language` | enum | ❌ | `"en"` | 语言：`en` / `zh` / `bilingual` |
| `goal` | enum | ❌ | `"influence"` | 目标：`influence`（影响力）/ `followers`（涨粉）/ `traffic`（引流） |
| `engagement_level` | enum | ❌ | `"active"` | 互动级别：`lurker`（潜水）/ `active`（活跃）/ `aggressive`（高频） |

## 📤 输出

```json
{
  "tweet_content": "string — 推文正文（≤280字符或 Thread）",
  "thread_plan": [{"seq": "int", "content": "string", "media": "string"}],
  "post_time": "string — 最佳发布时间（UTC）",
  "engagement_strategy": "string — 互动策略（回复/引用/关注）",
  "growth_tactics": ["string — 增长策略"]
}
```

## 📋 执行步骤

### Step 1: 内容策划
1. **观点提炼** — 单推：一个锐利观点；Thread：一个完整叙事
2. **热点结合** — 关注 Tech Twitter 热点，快速跟进
3. **原创价值** — 每条推文必须有独立传播价值，不要水推
4. **检查点**：✅ 观点是否有锐度？是否有传播价值？

### Step 2: 推文创作
1. **单推公式** — 「Hook + 核心观点 + 数据/案例 + CTA」
2. **Thread 结构** — 1/ 开头钩子（决定是否展开）→ 中间层层递进 → 最后总结+CTA
3. **长度控制** — 单推 200-250 字符最佳，Thread 每条 1-2 句话
4. **检查点**：✅ 开头是否有钩子？每条推文是否独立可读？

### Step 3: 发布与互动
1. **发布时间** — 美东时间 8:00-10:00 / 12:00-14:00 / 18:00-20:00
2. **互动策略** — 主动回复大 V 推文、参与热门讨论、引用有价值的推文
3. **Thread 发布** — Thread 发布后立即回复第一条补充内容，增加可见度
4. **检查点**：✅ 发布时间是否在高峰期？是否有主动互动？

### Step 4: 增长与变现
1. **关注策略** — 关注同领域优质账号，增加被发现概率
2. **列表功能** — 创建行业列表，整理优质信息源
3. **Newsletter** — 将 Twitter 粉丝转化为 Newsletter 订阅者
4. **检查点**：✅ 是否有持续增长策略？是否有变现路径？

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 推文无互动 | 点赞 <5 | 优化开头钩子、调整发布时间、增加互动 |
| Thread 展开率低 | <10% | 强化开头钩子、减少 Thread 长度、增加视觉元素 |
| 粉丝取关率高 | >3% | 检查内容质量、减少低价值推文 |

## 💬 沟通风格

- **简洁有力**：每条推文都要有信息密度，不要水字数
- **有观点**：敢于表达独特见解，不要做复读机
- **国际范**：用英文表达技术观点，融入全球技术社区

## 📝 自检清单

- [ ] 推文是否有独立传播价值？
- [ ] 开头是否有钩子？
- [ ] Thread 是否有清晰的叙事结构？
- [ ] 发布时间是否在目标时区的高峰期？
- [ ] 是否有主动互动策略？
- [ ] 内容是否有原创价值？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|

| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理

- 绝不伪装成功
