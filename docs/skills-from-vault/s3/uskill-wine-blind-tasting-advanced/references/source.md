# 葡萄酒盲品进阶

## 🎯 目标

> 通过系统化的感官训练，提升葡萄酒品种和产区的识别能力。

**核心价值**：盲品的核心不是天赋，是「看到 → 描述 → 推理」的训练。本 Skill 建立从感官观察到品种/产区判断的逻辑链路。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `tasting_notes` | string | ✅ | — | 品鉴笔记（外观/香气/口感/余味） |
| `context` | string | ❌ | — | 额外信息（价格范围/产区提示/餐食搭配） |
| `goal` | enum | ❌ | `"identification"` | 目标：`identification`（品种识别）/ `training`（训练建议）/ `analysis`（推理分析） |

## 📋 执行步骤

### Step 1: 感官观察
1. **外观** — 颜色深度/边缘色调/粘稠度（判断年份和品种）
2. **香气** — 一层（果香）/ 二层（发酵）/ 三层（陈年）香气
3. **口感** — 甜度/酸度/单宁/酒体/余味长度
4. **检查点**：✅ 观察是否全面？是否遗漏了关键特征？

### Step 2: 逻辑推理
1. **品种匹配** — 基于感官特征匹配可能的品种
2. **产区推断** — 基于品种 + 风格推断可能的产区
3. **年份估计** — 基于陈年特征判断大致年份
4. **检查点**：✅ 推理是否有逻辑链条？是否有多候选？

### Step 3: 不确定性管理
1. **置信度评估** — 对每个推断给出置信度
2. **替代方案** — 列出 2-3 个可能的品种/产区
3. **信息缺口** — 说明哪些信息不足影响了判断
4. **检查点**：✅ 是否承认了不确定性？是否有替代方案？

### Step 4: 训练建议
1. **弱点识别** — 哪些感官维度需要加强
2. **练习酒款** — 推荐用于训练的具体酒款
3. **专项练习** — 针对弱点的训练方法
4. **检查点**：✅ 训练建议是否具体？是否有可执行的练习？

## ⚠️ 边界约束

**硬性约束（必须遵守）**：
1. 品鉴时必须吐酒，不得过量饮酒
2. 不得为了面子而强行猜测，必须承认不确定
3. 品鉴笔记必须基于感官描述，不得使用主观评价

**软性约束（建议遵守）**：
1. 盲品前避免使用香水/强烈食物
2. 每次品鉴不超过 6 款酒

**人工兜底点**：
- 当健康原因不宜饮酒时，**必须**建议替代训练方式
- 当品鉴环境不佳时，**必须**标注环境影响

## ⚠️ 异常处理

| 异常 | 条件 | 处理方式 |
|------|------|----------|
| 无法分辨香气 | 一层香气不明显 | 建议进行香气训练（咖啡/水果对比） |
| 单宁判断困难 | 不确定单宁强度 | 用「抓涩感」替代「单宁高低」 |
| 品种混淆 | 两个品种特征相似 | 列出两个候选，说明区分要点 |


### 降级策略
- 当数据不足时，基于已有数据给出保守建议并标注置信度
- 当无法自动化时，输出分析框架供人工填充

## 💬 沟通风格

- **感官语言**：用具体的风味词汇（「黑色浆果」「雪松」「烟熏」）
- **逻辑链**：每个推断都有「因为…所以…」的推理过程
- **诚实**：不确定就说不确定，不装专家

- [ ] 每个推断有推理过程

- [ ] 未违反硬性约束

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
