# 代码审查

## 🎯 目标

> 通过结构化的代码审查流程，在代码合并前发现缺陷、提升质量、传播知识。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `review_scope` | enum | ❌ | `"full"` | 范围：`full`（完整审查）/ `security`（安全专项）/ `performance`（性能专项）/ `quick`（快速审查） |
| `language` | string | ❌ | — | 编程语言 |

## 📤 输出

```json
{
  "review_report": {
    "correctness": [{"file": "string", "line": "int", "issue": "string", "severity": "string"}],
    "security": [{"file": "string", "issue": "string", "severity": "string"}],
    "maintainability": ["string"],
    "performance": ["string"]
  },
  "verdict": "string — APPROVE / REQUEST_CHANGES / COMMENT"
}
```

## 📋 执行步骤

### Step 1: 正确性审查
1. **逻辑检查** — 边界条件、空值处理、错误路径
2. **并发安全** — 竞态条件、死锁、数据竞争
3. **数据一致性** — 事务边界、幂等性
4. **检查点**：✅ 边界条件是否处理？并发是否安全？

### Step 2: 安全审查
1. **输入验证** — SQL 注入/XSS/命令注入
2. **认证授权** — 权限检查是否完整
3. **敏感数据** — 日志/响应中是否泄露
4. **检查点**：✅ 输入是否验证？是否有注入风险？

### Step 3: 可维护性审查
1. **命名** — 变量/函数/类名是否清晰
2. **复杂度** — 函数是否过长/嵌套是否过深
3. **重复** — 是否有可提取的公共逻辑
4. **检查点**：✅ 命名是否清晰？复杂度是否可控？

### Step 4: 反馈与跟进
1. **建设性反馈** — 说明问题 + 建议修复方案
2. **严重分级** — BLOCKER/MAJOR/MINOR/SUGGESTION
3. **跟进验证** — 修复后重新审查
4. **检查点**：✅ 反馈是否建设性？是否分级标注？

## 💬 沟通风格
- **对事不对人**：说「这段代码」不说「你写的代码」
- **建设性**：指出问题的同时给出修复建议
- **尊重优先**：理解作者的意图，再提出改进

## 📝 自检清单
- [ ] 是否覆盖了正确性/安全/可维护性三个维度？
- [ ] 反馈是否建设性？
- [ ] 是否验证了边界条件？
- [ ] 严重程度是否分级？
- [ ] 安全漏洞是否已标注？

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
