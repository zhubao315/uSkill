# [[事件响应与故障处理]]

## 🎯 目标

> 建立从事件发现到复盘改进的标准化响应流程，将故障影响最小化。

## 📥 输入

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| `incident_type` | enum | ✅ | — | 类型：`service_down`（服务不可用）/ `degraded`（性能下降）/ `data_issue`（数据异常）/ `security`（安全事件） |
| `severity` | enum | ❌ | `"P1"` | 严重程度：`P0` / `P1` / `P2` / `P3` |
| `phase` | enum | ❌ | `"response"` | 阶段：`response`（响应）/ `postmortem`（复盘）/ `prevention`（预防） |

## 📤 输出

```json
{
  "response_plan": {
    "immediate_actions": ["string — 立即执行的动作"],
    "communication": "string — 对内/对外沟通方案",
    "escalation": "string — 升级路径"
  },
  "postmortem": {
    "timeline": "string — 事件时间线",
    "root_cause": "string — 根因分析",
    "impact": "string — 影响范围和时长",
    "action_items": [{"owner": "string", "action": "string", "deadline": "string"}]
  }
}
```

## 📋 执行步骤

### Step 1: 事件响应（15 分钟内）
1. **确认事件** — 验证是否为真实故障
2. **分级评估** — P0（全面中断）/ P1（核心功能受损）/ P2（部分受损）/ P3（轻微）
3. **止血优先** — 先恢复服务再查根因
4. **通知相关方** — 按通知矩阵通知
5. **检查点**：✅ 是否 15 分钟内响应？是否先止血？

### Step 2: 诊断与修复
1. **日志分析** — 查看错误日志和监控指标
2. **变更排查** — 最近的部署/配置变更
3. **修复方案** — 回滚/热修复/配置修改
4. **验证恢复** — 确认服务恢复正常
5. **检查点**：✅ 根因是否定位？修复是否验证？

### Step 3: 事后复盘（72 小时内）
1. **时间线** — 精确到分钟的事件时间线
2. **根因分析** — 5 Why 分析法
3. **影响评估** — 影响用户数/时长/业务损失
4. **改进项** — 每个改进项有负责人和截止日期
5. **检查点**：✅ 时间线是否精确？改进项是否有负责人？

### Step 4: 预防机制
1. **监控补全** — 事件暴露的监控盲区
2. **告警优化** — 误报/漏报调整
3. **预案更新** — 更新 Runbook
4. **演练** — 定期故障演练
5. **检查点**：✅ 监控是否补全？预案是否更新？

## 💬 沟通风格
- **冷静客观**：故障时不需要情绪化表达
- **透明公开**：对内对外同步信息
- **无责文化**：复盘不追责，追流程改进

#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
