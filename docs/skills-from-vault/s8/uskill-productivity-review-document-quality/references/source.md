# Review Document Quality Checklist (文档质量审查清单)

## 🎯 目标
> 通过 Why-Who-How-What 四维检查框架，在文档发布前系统性审查质量，确保文档目标明确、读者导向、结构清晰、内容精炼。

## 📥 输入

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `document_text` | string | ✅ | 待审查的文档原文（纯文本或 Markdown） |
| `document_type` | enum | ❌ | `report` / `proposal` / `email` / `blog` / `prd`，默认 `report` |
| `target_audience` | string | ❌ | 目标读者描述（如"高管""技术团队""协作者"） |
| `strictness` | enum | ❌ | `lenient` / `standard` / `strict`，默认 `standard` |

## 📤 输出

```json
{
  "overall_score": "int (0-100)",
  "dimension_scores": {
    "why": "int (0-100) — 目标清晰度",
    "who": "int (0-100) — 读者适配度",
    "how": "int (0-100) — 结构合理性",
    "what": "int (0-100) — 内容表达质量"
  },
  "issues": [
    {
      "severity": "critical | major | minor | suggestion",
      "dimension": "why | who | how | what",
      "description": "string — 问题描述",

    }
  ],

    {
      "priority": "high | medium | low",

```

## 📋 执行步骤

### Step 1: Why — 目标审查（权重 30%）

> 检查文档是否回答了"为什么要写这份文档"。

1. **识别核心问题** — 检查文档是否清晰阐述要解决的核心问题或传达的核心结论
2. **检查核心观点** — 验证主要论点/建议是否在前 20% 篇幅内出现，且不超过 3 个
3. **评估可执行性** — 检查文档是否包含明确的行动建议或决策依据（`report`/`proposal`/`prd` 类必查）

评分规则: 核心问题缺失 → ≤ 30 分；观点超过 3 个或不明确 → ≤ 60 分；建议缺失 → 扣 15 分。

### Step 2: Who — 读者审查（权重 25%）

> 检查文档是否以目标读者为中心。

4. **读者画像匹配** — 判断文档是否明确定义或暗示了目标读者（若有 `target_audience` 参数则对比检查）
5. **背景上下文充分性** — 检查是否为读者提供了理解所需的背景信息，避免知识诅咒
6. **角色关切覆盖** — 按角色类型检查覆盖度：

| 角色 | 核心关切 | 检查重点 |
|------|----------|----------|
| 决策者 | 方案全面性 / ROI / 风险 | 是否有方案对比、数据支撑、风险分析 |
| 协作者 | 影响 / 收益 / 配合 | 是否说明对他们工作的影响和需要的配合 |
| 信息同步者 | 关键信息 | 是否有简明摘要，可快速获取关键信息 |

7. **术语适配** — 行话和缩写是否对目标读者合适？首次出现的术语是否有解释？

评分规则: 未识别读者 → ≤ 25 分；背景信息不足 → 扣 20 分；术语未解释 → 每个扣 5 分。

### Step 3: How — 结构审查（权重 25%）

> 检查文档结构是否符合金字塔原理，便于快速获取信息。

8. **金字塔原理验证** — 检查是否采用"结论先行、分层论述"的结构
9. **结论前置检查** — 核心结论/摘要是否在文档开头 1-2 段出现
10. **目录/导航完整性** — 文档是否有清晰的目录或小标题体系（> 2000 字必查）
11. **逻辑链路清晰度** — 各章节之间逻辑关系是否清晰（因果 / 并列 / 递进）

评分规则: 无结构可言 → ≤ 20 分；结论未前置 → 扣 25 分；缺少目录 → 扣 10 分。

### Step 4: What — 内容审查（权重 20%）

> 分五个子维度逐项评估文档内容的表达质量。

12. **突出重点** — 关键结论是否前置？重要数据是否高亮或用图表呈现？每段是否有中心句？
13. **精简内容** — 运用"信息减损测试"：逐段检查，如果去掉某段/某句，读者是否明确意识到信息缺失？若答案不是明确的"是"，则该内容可删。去除已知信息、提取要点、消除冗余。
14. **清晰表达** — 句子是否简短明确？是否避免黑话和行话？是否预见读者疑问并在文中解答？
15. **格式检查** — 对齐一致性、错别字、标点符号、标题层级、列表样式是否全文统一？
16. **迭代优化** — 是否有修订痕迹或待办标记？建议收集反馈、学习优秀文档、避免重复错误。

评分规则: 每个子维度 20 分，满分 100 → 加权后乘以 20% 计入总分。

### Step 5: 评分汇总与建议生成

17. **计算加权总分** — `总分 = why × 0.30 + who × 0.25 + how × 0.25 + what × 0.20`
18. **应用 strictness 修正** — `strict` 模式: 任何维度 < 40 → 总分上限 60；`lenient` 模式: 总分 × 1.1（上限 100）
19. **生成改进建议** — 按维度优先级排序 issues，为每个 critical/major 问题生成可操作的修复建议
20. **确定评级** — ≥ 85 优秀 / ≥ 70 良好 / ≥ 50 及格 / < 50 需重写

## ⚠️ 异常处理

| 异常 | 处理 |
|------|------|
| `document_text` 为空 | 返回 `ERROR_EMPTY_INPUT`，终止执行 |
| 文档 < 100 字 | 返回 `WARNING_TOO_SHORT`，跳过 Step 3 结构审查，降低权重 |
| 文档 > 50000 字 | 采样审查：首尾各 5000 字 + 中间随机 3 段 × 3000 字 |
| 语言混合（中英混杂） | 标记 `WARNING_MIXED_LANGUAGE`，分别审查各语言段落 |
| 无法识别核心论点 | 标记 `WARNING_NO_THESIS`，Why 维度给低分，建议补充摘要 |
| 文档含大量代码块 | 代码块不计入结构/内容审查字数，仅审查注释和文档说明部分 |

## ✅ 自检清单

- [ ] 四维审查（Why / Who / How / What）全部完成，无遗漏
- [ ] 评分权重与公式逻辑自洽：总分 = why × 0.30 + who × 0.25 + how × 0.25 + what × 0.20
- [ ] 每个 issue 包含 `location` 字段，引用具体段落或行号
- [ ] 每个 suggestion 包含可操作的具体动作，非泛泛而谈
- [ ] 输出 JSON 结构符合上方 schema 定义，所有必填字段存在
- [ ] `checklist_results` 覆盖 Step 1-4 的所有检查项（共 16 项）
- [ ] `strictness` 参数对评分和过滤逻辑有实际影响
- [ ] 信息减损测试（Step 14）已对每个段落执行并记录结果


#### ⚠️ 边界约束

> 此区块定义此 Skill 的硬性限制和软性约束，确保执行不越界。

**硬性约束（必须遵守）**：
1. 不得违反相关法律法规和平台规则
2. 不得泄露用户隐私数据
3. 不得在未经验证的情况下做出不可逆决策

**软性约束（建议遵守）**：
1. 优先使用已验证的方法论，避免发明新轮子
2. 复杂决策应记录理由供后续审计

**人工兜底点**：
- 当输入数据质量不足以支撑自动化决策时，**必须**转交人工判断
- 当涉及法律/财务/医疗等高风险领域时，**必须**暂停执行等待确认

#### ✅ 校验验收规则

> 此区块定义执行后的验证标准，确保输出质量。

**格式校验**：
- [ ] 输出内容结构完整，无缺失区块
- [ ] 所有必填参数已填充
- [ ] 输出格式符合预定义规范

**内容校验**：
- [ ] 建议具有可操作性，非泛泛而谈
- [ ] 数据引用准确，无虚构内容
- [ ] 方案考虑了实际约束条件

**合规校验**：
- [ ] 未违反硬性约束
- [ ] 人工兜底点已正确识别
- [ ] 敏感信息已脱敏处理

#### 🔄 迭代触发条件

> 此区块定义 Skill 自我进化的触发机制。

**Self-Play 触发**：
- **频率**：monthly
- **触发条件**：
  - 用户反馈评分低于 7/10
  - 实际执行中发现新的异常场景
  - 相关领域出现重大变化

**版本升级触发**：
- 当新增 ≥3 种异常处理场景时，升级 minor 版本
- 当核心方法论发生根本性变化时，升级 major 版本

**废弃触发**：
- 当所依赖的平台/工具停止维护时，标记为 deprecated
- 当有更好的替代方案出现时，评估迁移

## 🛡️ Three-Tier Boundaries `[v3新增]`

> 来源：addyosmani/agent-skills 的边界系统

### ✅ Always do（自动执行）
- 执行核心功能（见原技能流程）
- 输出结构化结果
- 检查常见错误

### ⚠️ Ask first（先问再做）
- 用户意图不明确时
- 操作不可逆时
- 涉及外部系统时

### 🚫 Never do（绝对禁止）
- 不跳过验证步骤
- 不在用户未确认时执行高风险操作
- 不伪装成功（失败就上报）

## 🔒 Gated Workflow `[v3新增]`

> 来源：addyosmani 的门禁 + claude-skills 的 Agent Harness

```
DISCUSS → PLAN → EXECUTE → VERIFY → CLOSE
   ↓         ↓        ↓          ↓        ↓
 Context   方案     执行      证据     Done/
 Read     确认     任务      检查    Escalate
```

### Phase 1: DISCUSS
- [ ] 输出 Context Read 一行判断
- [ ] 确认用户意图
- [ ] 确认约束条件

### Phase 2: PLAN
- [ ] 制定执行方案
- [ ] 确认资源可用
- [ ] 人工审批计划

### Phase 3: EXECUTE
- [ ] 逐个任务实现
- [ ] 每步有输出记录

### Phase 4: VERIFY
- [ ] 检查核心输出
- [ ] 验证完整性
- [ ] 输出证据

### Phase 5: CLOSE
- [ ] 所有检查通过 → 标记完成
- [ ] 有未通过项 → 升级给人类
- [ ] 预算耗尽 → 强制升级，不伪装成功

## 🔄 IF/THEN 决策分支

- IF 输入数据质量不足以支撑自动化决策 → THEN 转交人工判断，输出不确定性说明
- IF 执行过程中遇到未预期的异常 → THEN 记录异常 + 降级处理 + 升级给人类
- IF 输出结果置信度 < 0.6 → THEN 标记低置信度 + 要求人工验证
- ELSE（所有检查通过）→ THEN 输出结果 + 验证证据

## 🧪 Self-Play 测试用例

| # | 场景 | 输入 | 预期输出 | 验证点 |
|---|------|------|----------|--------|
| 1 | 正常执行 | 标准输入数据 | 符合预期的输出 | 格式正确 + 内容准确 |
| 2 | 边界输入 | 极端/空/超长输入 | 降级处理或错误提示 | 不崩溃 + 有明确反馈 |
| 3 | 数据缺失 | 缺少必填参数 | 参数补全提示 | 不编造数据 |
| 4 | 异常场景 | 非预期的输入类型 | 友好的错误处理 | 不泄露内部信息 |
| 5 | 并发场景 | 多个相同请求同时到达 | 结果一致或正确排队 | 无数据竞争 |

## 📋 Verification Evidence `[v3新增]`

> 来源：addyosmani 的证据要求 + claude-skills 的 verify

### 完成标志
- [ ] 核心输出已生成
- [ ] 输出格式符合预期
- [ ] 无明显错误

### 失败处理
- 输出不完整 → 继续补充，不标记完成
- 连续 3 次失败 → 升级给人类，附上当前状态
- 绝不伪装成功
